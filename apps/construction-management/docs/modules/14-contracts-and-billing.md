# 14 — Contracts & Billing

The build spec for **M11 part 1** (CM-1101 … CM-1111): the Company's Item Library, a Project's BOQ and Variations, Work Orders, the Measurement Book, client and contractor RA bills, advances, retention, escalation and material reconciliation. It lives in the `contracts` context (`src/contracts`, Postgres schema `construction_contracts`, API prefix `/api/construction/contracts`).

The product decisions are in [ADR CM-0023](../adr/CM-0023-india-compliance-product-decisions.md) (§1–§10, §22). This page does not repeat them. It records the smaller decisions each ticket had to make while building, which the ADR left open. Each ticket appends its own list below.

## Decisions for the build (M11)

### CM-1102 — Item Library

- **Where it sits.** Master records gains a **Contracts** group holding **Item Library** (`/app/masters/item-library`). It matches the Contracts sidebar heading and the Contracts & Billing permission category. Later contracts masters (price indices for escalation, §9) can join it. Placing it beside Materials would mix what you buy with what you bill.
- **List order.** Items are listed in **code order**, not newest first, because a schedule is looked up by its code. The cursor carries the code and id. The total counts the filter.
- **Search and filter.** The search matches part of the code, the short description or the long description, ignoring case. The schedule filter is an exact match on one schedule label from the distinct live labels (`GET …/items/schedules`).
- **Limits.** Code ≤ 32 characters, short description ≤ 200, long description ≤ 4,000 (it keeps its line breaks), schedule ≤ 80, at most 100 analysis lines, a line description ≤ 200. SAC/HSN is 4–8 digits.
- **Money and numbers.** Rates, line amounts and the analysed rate are integer paise from ₹0 to **₹1,000 crore** (10¹³ paise). That keeps every figure exact as a JSON number, the way other contexts send `BIGINT` money. Sums run in `bigint`. A coefficient is more than 0 and at most 10,00,000, with four places, and is sent as a string (`"0.4500"`). The overhead and profit is 0–100 % with two places (`"15.00"`).
- **Rounding.** A line's amount is `round(coefficient × rate)`. The analysed rate is `round(Σ amounts × (1 + overhead / 100))`, rounded once over the sum. Both round half up. The form works it out the same way while you type.
- **Lines by kind.** A line keeps only the reference its kind needs; any other reference sent is dropped. A **lump sum** has coefficient 1, no resource UoM, and a required description. Its rate is per Item unit. A **material line** without a resource UoM takes the Material's UoM.
- **Picked masters.** A Material, Labour Category, Equipment or UoM must belong to the Company and be live and enabled. One the Item already has may stay after it is disabled or removed, so an old Item can still be saved. The same applies to the Item's own UoM. The errors are 400 `ITEM_UOM_INVALID` and `ANALYSIS_{MATERIAL,LABOUR_CATEGORY,EQUIPMENT,UOM}_INVALID`, with `details.line` (from 0) and `details.field` (`lines.N.materialId`).
- **Overhead without lines.** The overhead is stored as typed even with no lines. The analysed rate is null without lines.
- **Rate suggestions.** Picking a Material on a material line fills a blank rate with the Material's unit rate. This happens only when the caller holds the **Materials** menu's Financial flag; otherwise the picker sends no rate. Labour Categories have no wage in Master records, so labour lines get no suggestion. CM-1118's minimum-wage cards can add one later.
- **Pickers.** The form reads its UoMs, Labour Categories and Equipment from `GET …/items/form-options` and Materials from `GET …/items/material-options` (a server search). Both need Item Library create or update, so a Team Member without Materials or Equipment read can still build an analysis. Materials, Labour Categories and Equipment are pickers you can search. UoMs are a plain select.
- **Flags on screen.** The list response carries `viewerFlags`: the Item Library flags the caller holds. The screen hides Add, Edit, Delete, Import, Sample and Export by them. Every route checks again. (`…/contracts/access` needs a Project, and the Item Library is Company-wide.) A Team Member with View only sees the list, and codes are not links.
- **Delete guard.** Delete locks the Item row, then counts live BOQ items (`boq_items.item_id`, `deleted_at IS NULL`) in the same transaction. 409 `ITEM_IN_USE` carries `details.count`. CM-1103 should take the same row lock (or `FOR SHARE`) when it copies an Item into a BOQ.
- **Optimistic checks.** Update needs `expectedUpdatedAt` (409 `ITEM_CHANGED`). Delete checks it when sent. Update replaces every analysis line in the same transaction; the lines get new ids.
- **Import.** The sheet's columns are Code, Short description, Description, UoM, SAC/HSN, Schedule and Rate (₹), found by header, so the order is free. Rows match Items by Code, ignoring case. A new code adds an Item with no analysis. An existing code has its fields replaced, and a blank optional cell clears that field. Its analysis lines, overhead and analysed rate stay. A row identical to its Item counts as `unchanged`. The UoM is matched by **name** ignoring case, because Measurement Units have no symbol column. An existing Item may keep a UoM that has since been disabled. A code twice in one sheet is a row error naming the first row. The rate is rupees with at most two places: a number cell, or text like `6,123.45` or `₹6123.45`. The import is all or nothing: 400 `IMPORT_HAS_ERRORS` with `details.errors = [{ row, column, message }]`, where `column` is the sample's header. Each row reports one problem per column. At most 2,000 rows and 5 MB, `.xlsx` only.
- **Import audit.** An import writes one `item.created` or `item.updated` audit event per changed Item, marked `source: "import"`, in one `createMany`.
- **Sample and export.** The sample has the headers and two example rows (a CPWD DSR item and an "Own" item). Downloading it needs the **Import** flag. The export writes the list's current search and schedule in the sample's columns, in code order, so it can be edited and imported back. It needs the **Export** flag and holds at most 10,000 Items (400 `EXPORT_TOO_MANY`).
- **Not yet.** Backups (CM-907) do not include the Item Library yet. A later contracts ticket adds the contracts tables to the backup modules together.

### CM-1103 — BOQ

- **Where it is.** Project → Contracts → **BOQ** (`/app/projects/{id}/boq`), one page with three tabs: **Items** (the sections), **Variations** and **Deviations**. `?tab=variations` opens the Variations, which is where a Variation's notification links. The total bar above the tabs shows the BOQ total, the Project's Order Value and the difference (total − Order Value).
- **HTTP shape.** Everything is under `/api/construction/contracts/boq`. Collection reads and creates name the Project (`?projectId=`, or `projectId` in the JSON body), and records use their id (`/sections/{id}`, `/items/{id}`, `/variations/{id}`), like the sales module. Access is checked first: 403 `PERMISSION_DENIED` for a Team Member not on the Project, then 404 `PROJECT_NOT_FOUND` for a Project that is not the Company's. A record of another Company is its own 404 (`BOQ_SECTION_NOT_FOUND`, `BOQ_ITEM_NOT_FOUND`, `VARIATION_NOT_FOUND`). Updates are named operations (`…/update`, `…/move`, `…/delete`, `…/approve`, `…/reject`, `settings/update`), like every other module, rather than `PUT`.
- **One read for the whole BOQ.** `GET …/boq?projectId=` answers every live section and item in order, with subtotals, the total, the measured flags and any pending Variation per item. A BOQ is a document read as a whole, so it is not paged. An import is capped at 5,000 rows.
- **One writer per BOQ.** Every BOQ and Variation command first takes a transaction advisory lock on the Project's BOQ (`construction_contracts.boq:{workspace}:{project}`). That settles positions, item numbers, the measured check and "one pending change per item" without new indexes. The partial unique indexes on titles and numbers are still the last word (P2002 → 409).
- **Limits and numbers.** A section title is at most 120 characters. An item no is at most 32, and a description at most 4,000 (line breaks kept). SAC/HSN is 4–8 digits. A quantity is more than 0 with four places, below 10¹², sent as a string (`"12.5000"`). A rate is integer paise from ₹0 to ₹1,000 crore, and a line's amount (`round(quantity × rate)`, half up) is at most ₹1,000 crore (400 `BOQ_AMOUNT_TOO_LARGE`). Subtotals and the total are sums of the rounded lines.
- **Original and current.** A new item's original quantity and rate are the ones given. Before any checked measurement, an edit corrects the contract: the original moves with the current figure while the two are still equal. Once an approved Variation has made them differ, an edit changes only the current figure.
- **Measured.** An item is measured when a row of a live measurement sheet with status `checked` names it (`measurement_rows.boq_item_id`). Measurement rows that name BOQ items are the client side, so the side is not filtered again. Once it is measured, a new quantity or rate (by the form or by import) is refused with 409 `BOQ_ITEM_MEASURED`, and so is a delete. The item no, description, UoM, SAC/HSN, Wing or Location and section stay editable. The measured quantity is the sum of those rows (deductions included). The check runs inside the BOQ lock. CM-1105 should take the same lock (or lock the item rows) when it checks a sheet, so a check and an edit cannot cross.
- **Wing or Location.** An item may name a Wing on a building Project or a Location on one with Locations (by `structure` from the directory), never both (400 `BOQ_ITEM_PLACE_INVALID`). A Wing or Location the item already has may stay after it is removed.
- **Item Library copy.** The form's picker reads `GET …/boq/library-items` (code or description, 25 at a time). It needs BOQ create or update, not Item Library read. The adopted rate is sent only with BOQ Financial. Picking fills the item no (when blank) with the code, the description (the long one, or the short one), the UoM, SAC/HSN and the rate, and they can be changed. The create sends `libraryItemId`. The server locks that Item `FOR SHARE` inside the transaction (`lockLibraryItems`), so CM-1102's delete (`FOR UPDATE`, then count) either waits and sees the new BOQ item (409 `ITEM_IN_USE`), or runs first and the copy gets 400 `BOQ_LIBRARY_ITEM_NOT_FOUND`. The HTTP test races the two six times.
- **Moves.** Sections and items move one place up or down (an item within its section), and positions are renumbered 0…n. Changing an item's section puts it at the end of the new one.
- **Delete guards.** A section is deleted only with no live items (409 `BOQ_SECTION_NOT_EMPTY`, `details.count`) and no pending extra item joining it (409 `VARIATION_PENDING`). An item cannot be deleted while a Variation of it is pending (409 `VARIATION_PENDING`). Deletes are tombstones, and the title or number is free again.
- **Financial.** Without BOQ Financial, every rate, amount, subtotal, total, the Order Value and the difference are `null`, and so are a Variation's rates and the library's adopted rate. The page shows quantities only. Without Financial the rate field is not shown and the server ignores any rate sent: a copied item gets the library's adopted rate, a typed one ₹0, and an edit keeps the rate. Rate changes and extra items need Financial (403), quantity changes do not. The Excel sample, import and export need Financial as well as their own flag (403), because the file carries rates.
- **Variations.** Numbers come from the `variation` sequence rule for the Project (`VAR/26-27/00001`), dated the Company's today, allocated inside the create's transaction. A Variation is raised with BOQ create. The reason is required (≤ 500). Each kind keeps only its own fields. A quantity or rate change records the figure it replaces at creation and again at approval. An extra item's number must be free among live items and other pending extra items (409 `BOQ_ITEM_NO_TAKEN`), checked again at approval. At most one pending quantity or rate change per item, whichever kind (409 `VARIATION_PENDING`, `details.number`). Approve and Reject use the approval kernel (`approve` / `reject`, `VARIATION_NOT_PENDING`, `REJECTION_REASON_REQUIRED`) with the BOQ's Approve and Reject flags. There is no Save & Approve, and the approver may be the creator. Approval applies the change in the same transaction, and an extra item becomes a BOQ item at the end of its section with `variation_id` set. A pending Variation can be edited (its kind is fixed) or deleted by whoever raised it while they hold BOQ create, or by a holder of BOQ update. Decided ones are final.
- **Notifications.** A Variation dispatches `document.submitted|approved|rejected` with the approval type `variation` (`APPROVAL_DOCUMENTS`, menu `contracts.boq`, link `…/boq?tab=variations`). Messaging turns these into `approval.requested` and `approval.decided` rather than a separate `variation.pending_approval` type. The BOQ menu has no Notification flag (CM-0023 §4: CRUDAJPOFEI), so, like Other Expenses, only the **Owner** is asked to approve. For the same reason, the creator hears of the decision only when they are the Owner. Adding N to the BOQ menu would let approvers be notified. That needs the menu letters, the designation templates and the CM-1101 access test changed together, so it is left for the product owner to decide.
- **Deviation limit.** The Company's limit is in `construction_contracts.settings` (default 25 %, 0–100 with two places). `GET …/boq/settings` needs BOQ read, and `POST …/boq/settings/update` needs BOQ **Update**. Both are checked at Company level (the flag in the matrix, on no particular Project), because the setting covers every Project. The deviation list (`GET …/boq/deviations`) holds items whose checked measured quantity is more than `current × (1 + limit / 100)`, in BOQ order, with the % over (two places, half up) and any pending Variation. "Raise variation" opens a quantity change filled with the measured quantity.
- **Import.** One sheet (`BOQ`). Columns are found by header: Section, Item no, Description, UoM, SAC/HSN, Quantity, Rate (₹), Wing / Location, Library code. Sections are matched by title ignoring case, and new ones are added in first-seen order. Items are matched by Item no ignoring case. A new number adds an item at the end of its section. An existing number has its fields replaced (and moves to the end of a new section). A row identical to its item counts as `unchanged`. A Library code links the Item and fills blank Description, UoM, SAC/HSN and Rate from it. A blank code unlinks it. The UoM is matched by name, and the Wing or Location by name (an ambiguous name is a row error). A measured item's new quantity or rate is a row error on that column. Everything runs in one transaction inside the BOQ lock: all or nothing, 400 `IMPORT_HAS_ERRORS` with `details.errors` = [{ row, column, message }], at most 5,000 rows and 5 MB. The import writes one audit event per changed section and item (`source: "import"`) and one `boq.imported` summary.
- **Export.** The whole BOQ in order, with Original quantity, Quantity, Original rate (₹), Rate (₹) and Amount (₹) beside the sample's columns. Its Quantity and Rate (₹) columns import back unchanged, and the extra columns are ignored.
- **Audit.** `boq_section.created|renamed|moved|deleted`, `boq_item.created|updated|moved|deleted` (an approval's change carries `variationId`), `variation.created|updated|deleted|approved|rejected`, `contracts_settings.updated` and `boq.imported`.
- **No schema change.** The CM-1101 tables were enough. "One pending change per item" is kept by the lock, not a partial index.
- **Not yet.** Backups (CM-907) do not include the BOQ yet, as with the Item Library. Work Orders (CM-1104) should refuse to delete or renumber a BOQ item their lines name.
