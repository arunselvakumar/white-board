# 14 — Contracts & Billing

The build spec for **M11 part 1** (CM-1101 … CM-1111): the Company's Item Library, a Project's BOQ and Variations, Work Orders, the Measurement Book, client and contractor RA bills, advances, retention, escalation and material reconciliation. It lives in the `contracts` context (`src/contracts`, Postgres schema `construction_contracts`, API prefix `/api/construction/contracts`).

The product decisions are in [ADR CM-0023](../adr/CM-0023-india-compliance-product-decisions.md) (§1–§10, §22). This page does not repeat them. It records the smaller decisions each ticket had to make while building, which the ADR left open. Each ticket appends its own list below.

## Decisions for the build (M11)

### CM-1102 — Item Library

- **Where it sits.** Master records gains a **Contracts** group holding **Item Library** (`/app/masters/item-library`). It matches the Contracts sidebar heading and the Contracts & Billing permission category. Later contracts masters (price indices for escalation, §9) can join it. Placing it beside Materials would mix what you buy with what you bill.
- **List order.** Items are listed in **code order**, not newest first, because a schedule is looked up by its code. The cursor carries the code and id. The total counts the filter.
- **Search and filter.** The search matches part of the code, the short description or the long description, ignoring case. The schedule filter is an exact match on one schedule label from the distinct live labels (`GET …/items/schedules`).
- **Limits.** Code ≤ 32 characters, short description ≤ 200, long description ≤ 4,000 (it keeps its line breaks), schedule ≤ 80, at most 100 analysis lines, a line description ≤ 200. SAC/HSN is 4–8 digits.
- **Money and numbers.** Rates, line amounts and the analysed rate are integer paise from ₹0 to **₹1,000 crore** (10¹³ paise). That keeps every figure exact as a JSON number, the way other contexts send `BIGINT` money. Sums run in `bigint`. A coefficient is more than 0 and at most 10,00,000, with four places, and is sent as a string (`"0.4500"`). The overhead and profit is 0–100 % with two places (`"15.00"`).
- **Rounding.** A line's amount is `round(coefficient × rate)`. The analysed rate is `round(Σ amounts × (1 + overhead / 100))`, rounded once over the sum. Both round half up. The form works it out the same way while you type.
- **Lines by kind.** A line keeps only the reference its kind needs; any other reference sent is dropped. A **lump sum** has coefficient 1, no resource UoM, and a required description. Its rate is per Item unit. A **material line** without a resource UoM takes the Material's UoM.
- **Picked masters.** A Material, Labour Category, Equipment or UoM must belong to the Company and be live and enabled. One the Item already has may stay after it is disabled or removed, so an old Item can still be saved. The same applies to the Item's own UoM. The errors are 400 `ITEM_UOM_INVALID` and `ANALYSIS_{MATERIAL,LABOUR_CATEGORY,EQUIPMENT,UOM}_INVALID`, with `details.line` (from 0) and `details.field` (`lines.N.materialId`).
- **Overhead without lines.** The overhead is stored as typed even with no lines. The analysed rate is null without lines.
- **Rate suggestions.** Picking a Material on a material line fills a blank rate with the Material's unit rate. This happens only when the caller holds the **Materials** menu's Financial flag; otherwise the picker sends no rate. Labour Categories have no wage in Master records, so labour lines get no suggestion. CM-1118's minimum-wage cards can add one later.
- **Pickers.** The form reads its UoMs, Labour Categories and Equipment from `GET …/items/form-options` and Materials from `GET …/items/material-options` (a server search). Both need Item Library create or update, so a Team Member without Materials or Equipment read can still build an analysis. Materials, Labour Categories and Equipment are pickers you can search. UoMs are a plain select.
- **Flags on screen.** The list response carries `viewerFlags`: the Item Library flags the caller holds. The screen hides Add, Edit, Delete, Import, Sample and Export by them. Every route checks again. (`…/contracts/access` needs a Project, and the Item Library is Company-wide.) A Team Member with View only sees the list, and codes are not links.
- **Delete guard.** Delete locks the Item row, then counts live BOQ items (`boq_items.item_id`, `deleted_at IS NULL`) in the same transaction. 409 `ITEM_IN_USE` carries `details.count`. CM-1103 should take the same row lock (or `FOR SHARE`) when it copies an Item into a BOQ.
- **Optimistic checks.** Update needs `expectedUpdatedAt` (409 `ITEM_CHANGED`). Delete checks it when sent. Update replaces every analysis line in the same transaction; the lines get new ids.
- **Import.** The sheet's columns are Code, Short description, Description, UoM, SAC/HSN, Schedule and Rate (₹), found by header, so the order is free. Rows match Items by Code, ignoring case. A new code adds an Item with no analysis. An existing code has its fields replaced, and a blank optional cell clears that field. Its analysis lines, overhead and analysed rate stay. A row identical to its Item counts as `unchanged`. The UoM is matched by **name** ignoring case, because Measurement Units have no symbol column. An existing Item may keep a UoM that has since been disabled. A code twice in one sheet is a row error naming the first row. The rate is rupees with at most two places: a number cell, or text like `6,123.45` or `₹6123.45`. The import is all or nothing: 400 `IMPORT_HAS_ERRORS` with `details.errors = [{ row, column, message }]`, where `column` is the sample's header. Each row reports one problem per column. At most 2,000 rows and 5 MB, `.xlsx` only.
- **Import audit.** An import writes one `item.created` or `item.updated` audit event per changed Item, marked `source: "import"`, in one `createMany`.
- **Sample and export.** The sample has the headers and two example rows (a CPWD DSR item and an "Own" item). Downloading it needs the **Import** flag. The export writes the list's current search and schedule in the sample's columns, in code order, so it can be edited and imported back. It needs the **Export** flag and holds at most 10,000 Items (400 `EXPORT_TOO_MANY`).
- **Not yet.** Backups (CM-907) do not include the Item Library yet. A later contracts ticket adds the contracts tables to the backup modules together.

### CM-1103 — BOQ

- **Where it is.** Project → Contracts → **BOQ** (`/app/projects/{id}/boq`), one page with three tabs: **Items** (the sections), **Variations** and **Deviations**. `?tab=variations` opens the Variations, which is where a Variation's notification links. The total bar above the tabs shows the BOQ total, the Project's Order Value and the difference (total − Order Value).
- **HTTP shape.** Everything is under `/api/construction/contracts/boq`. Collection reads and creates name the Project (`?projectId=`, or `projectId` in the JSON body), and records use their id (`/sections/{id}`, `/items/{id}`, `/variations/{id}`), like the sales module. Access is checked first: 403 `PERMISSION_DENIED` for a Team Member not on the Project, then 404 `PROJECT_NOT_FOUND` for a Project that is not the Company's. A record of another Company is its own 404 (`BOQ_SECTION_NOT_FOUND`, `BOQ_ITEM_NOT_FOUND`, `VARIATION_NOT_FOUND`). Updates are named operations (`…/update`, `…/move`, `…/delete`, `…/approve`, `…/reject`, `settings/update`), like every other module, rather than `PUT`.
- **One read for the whole BOQ.** `GET …/boq?projectId=` answers every live section and item in order, with subtotals, the total, the measured flags and any pending Variation per item. A BOQ is a document read as a whole, so it is not paged. An import is capped at 5,000 rows.
- **One writer per BOQ.** Every BOQ and Variation command first takes a transaction advisory lock on the Project's BOQ (`construction_contracts.boq:{workspace}:{project}`). That settles positions, item numbers, the measured check and "one pending change per item" without new indexes. The partial unique indexes on titles and numbers are still the last word (P2002 → 409).
- **Limits and numbers.** A section title is at most 120 characters. An item no is at most 32, and a description at most 4,000 (line breaks kept). SAC/HSN is 4–8 digits. A quantity is more than 0 with four places, below 10¹², sent as a string (`"12.5000"`). A rate is integer paise from ₹0 to ₹1,000 crore, and a line's amount (`round(quantity × rate)`, half up) is at most ₹1,000 crore (400 `BOQ_AMOUNT_TOO_LARGE`). Subtotals and the total are sums of the rounded lines.
- **Original and current.** A new item's original quantity and rate are the ones given. Before any checked measurement, an edit corrects the contract: the original moves with the current figure while the two are still equal. Once an approved Variation has made them differ, an edit changes only the current figure.
- **Measured.** An item is measured when a row of a live measurement sheet with status `checked` names it (`measurement_rows.boq_item_id`). Measurement rows that name BOQ items are the client side, so the side is not filtered again. Once it is measured, a new quantity or rate (by the form or by import) is refused with 409 `BOQ_ITEM_MEASURED`, and so is a delete. The item no, description, UoM, SAC/HSN, Wing or Location and section stay editable. The measured quantity is the sum of those rows (deductions included). The check runs inside the BOQ lock. CM-1105 should take the same lock (or lock the item rows) when it checks a sheet, so a check and an edit cannot cross.
- **Wing or Location.** An item may name a Wing on a building Project or a Location on one with Locations (by `structure` from the directory), never both (400 `BOQ_ITEM_PLACE_INVALID`). A Wing or Location the item already has may stay after it is removed.
- **Item Library copy.** The form's picker reads `GET …/boq/library-items` (code or description, 25 at a time). It needs BOQ create or update, not Item Library read. The adopted rate is sent only with BOQ Financial. Picking fills the item no (when blank) with the code, the description (the long one, or the short one), the UoM, SAC/HSN and the rate, and they can be changed. The create sends `libraryItemId`. The server locks that Item `FOR SHARE` inside the transaction (`lockLibraryItems`), so CM-1102's delete (`FOR UPDATE`, then count) either waits and sees the new BOQ item (409 `ITEM_IN_USE`), or runs first and the copy gets 400 `BOQ_LIBRARY_ITEM_NOT_FOUND`. The HTTP test races the two six times.
- **Moves.** Sections and items move one place up or down (an item within its section), and positions are renumbered 0…n. Changing an item's section puts it at the end of the new one.
- **Delete guards.** A section is deleted only with no live items (409 `BOQ_SECTION_NOT_EMPTY`, `details.count`) and no pending extra item joining it (409 `VARIATION_PENDING`). An item cannot be deleted while a Variation of it is pending (409 `VARIATION_PENDING`). Deletes are tombstones, and the title or number is free again.
- **Financial.** Without BOQ Financial, every rate, amount, subtotal, total, the Order Value and the difference are `null`, and so are a Variation's rates and the library's adopted rate. The page shows quantities only. Without Financial the rate field is not shown and the server ignores any rate sent: a copied item gets the library's adopted rate, a typed one ₹0, and an edit keeps the rate. Rate changes and extra items need Financial (403), quantity changes do not. The Excel sample, import and export need Financial as well as their own flag (403), because the file carries rates.
- **Variations.** Numbers come from the `variation` sequence rule for the Project (`VAR/26-27/00001`), dated the Company's today, allocated inside the create's transaction. A Variation is raised with BOQ create. The reason is required (≤ 500). Each kind keeps only its own fields. A quantity or rate change records the figure it replaces at creation and again at approval. An extra item's number must be free among live items and other pending extra items (409 `BOQ_ITEM_NO_TAKEN`), checked again at approval. At most one pending quantity or rate change per item, whichever kind (409 `VARIATION_PENDING`, `details.number`). Approve and Reject use the approval kernel (`approve` / `reject`, `VARIATION_NOT_PENDING`, `REJECTION_REASON_REQUIRED`) with the BOQ's Approve and Reject flags. There is no Save & Approve, and the approver may be the creator. Approval applies the change in the same transaction, and an extra item becomes a BOQ item at the end of its section with `variation_id` set. A pending Variation can be edited (its kind is fixed) or deleted by whoever raised it while they hold BOQ create, or by a holder of BOQ update. Decided ones are final.
- **Notifications.** A Variation dispatches `document.submitted|approved|rejected` with the approval type `variation` (`APPROVAL_DOCUMENTS`, menu `contracts.boq`, link `…/boq?tab=variations`). Messaging turns these into `approval.requested` and `approval.decided` rather than a separate `variation.pending_approval` type. CM-1103 gave the BOQ menu the **Notification** flag (CRUDAJPNOFEI; ADR CM-0023 §4 updated), so a new Variation reaches the holders of BOQ Approve and Notification on the Project, and its creator hears of the decision when they hold BOQ Read and Notification. The Owner always does. The seeded Admin and Project Manager templates hold BOQ Notification, in `designations.json` and in the unshipped M11 menus migration (`20261021090500`), which was edited in place.
- **Deviation limit.** The Company's limit is in `construction_contracts.settings` (default 25 %, 0–100 with two places). `GET …/boq/settings` needs BOQ read, and `POST …/boq/settings/update` needs BOQ **Update**. Both are checked at Company level (the flag in the matrix, on no particular Project), because the setting covers every Project. The deviation list (`GET …/boq/deviations`) holds items whose checked measured quantity is more than `current × (1 + limit / 100)`, in BOQ order, with the % over (two places, half up) and any pending Variation. "Raise variation" opens a quantity change filled with the measured quantity.
- **Import.** One sheet (`BOQ`). Columns are found by header: Section, Item no, Description, UoM, SAC/HSN, Quantity, Rate (₹), Wing / Location, Library code. Sections are matched by title ignoring case, and new ones are added in first-seen order. Items are matched by Item no ignoring case. A new number adds an item at the end of its section. An existing number has its fields replaced (and moves to the end of a new section). A row identical to its item counts as `unchanged`. A Library code links the Item and fills blank Description, UoM, SAC/HSN and Rate from it. A blank code unlinks it. The UoM is matched by name, and the Wing or Location by name (an ambiguous name is a row error). A measured item's new quantity or rate is a row error on that column. Everything runs in one transaction inside the BOQ lock: all or nothing, 400 `IMPORT_HAS_ERRORS` with `details.errors` = [{ row, column, message }], at most 5,000 rows and 5 MB. The import writes one audit event per changed section and item (`source: "import"`) and one `boq.imported` summary.
- **Export.** The whole BOQ in order, with Original quantity, Quantity, Original rate (₹), Rate (₹) and Amount (₹) beside the sample's columns. Its Quantity and Rate (₹) columns import back unchanged, and the extra columns are ignored.
- **Audit.** `boq_section.created|renamed|moved|deleted`, `boq_item.created|updated|moved|deleted` (an approval's change carries `variationId`), `variation.created|updated|deleted|approved|rejected`, `contracts_settings.updated` and `boq.imported`.
- **No schema change.** The CM-1101 tables were enough. "One pending change per item" is kept by the lock, not a partial index.
- **Not yet.** Backups (CM-907) do not include the BOQ yet, as with the Item Library. Work Orders (CM-1104) should refuse to delete or renumber a BOQ item their lines name.

### CM-1104 — Work Orders

- **Where it is.** Project → Contracts → **Work Orders** (`/app/projects/{id}/work-orders`), with `/new`, `/{workOrderId}`, `/{workOrderId}/edit` (a draft) and `/{workOrderId}/amend` (an issued one). Approval notices link to the detail page.
- **HTTP shape.** Everything is under `/api/construction/contracts/work-orders`, Project-scoped like the BOQ: the list, create, `form-options`, `boq-items` and `material-options` name the Project (`?projectId=` or the body), and a Work Order is reached by its id (`/{id}`, `/{id}/update|delete|submit|approve|reject|amend|close|cancel`, `/{id}/pdf`). Access is checked first (403 `PERMISSION_DENIED`, then 404 `PROJECT_NOT_FOUND`); another Company's Work Order is 404 `WORK_ORDER_NOT_FOUND`. Every step answers with the whole Work Order, its warnings included.
- **Number.** A draft has **no number** (screens show “Draft”). The first submission takes one from the `work_order` sequence rule for the Project, dated the **order date** (so the fiscal-year token follows it). A rejection sends it back to draft and it keeps its number; a resubmission does not take another. A deleted draft's number is not reissued. No other numbered document had a draft state, so this needed `work_orders.number` to become nullable (the live-number partial unique index ignores nulls).
- **Migration `20261022090000_construction_contracts_work_order_advance_terms`** (`construction_contracts` only): `mobilisation_advance BIGINT NULL`, `mobilisation_recovery_percent DECIMAL(5,2) NULL`, `close_reason TEXT NULL` (the close reason had no column) and `number` nullable. Deployed to `construction_m11` and `construction_test_m11`.
- **Back-dated entry.** Work Orders join the policy as module `work_order` (“Work Order (WO)”, a new **Contracts** group, entry date `orderDate`, menu `contracts.work_orders`). A create checks the order date; an edit or amendment checks the stored date and, when it changes, the new one. Submit, approve, reject, close and cancel are not date edits and are not checked.
- **Parties.** The Contractor must be active and assigned to the Project (`ContractsDirectory.contractors`, 400 `WORK_ORDER_CONTRACTOR_INVALID`); one the Work Order already has may stay after it leaves the Project. The Department must be one of that Contractor's (400 `WORK_ORDER_DEPARTMENT_INVALID`), active or already on the Work Order. An amendment cannot change the Contractor (400 `WORK_ORDER_CONTRACTOR_FIXED`): cancel and raise a new one.
- **Terms.** Retention 0–100 % (blank 0), cap 0–100 % of value (blank: none), released on completion 0–100 % (blank 50), DLP 0–120 whole months, mobilisation recovery 0–100 %, all with two places. **GST** is a free 0–28 % with two places, matching the existing GST inputs (Materials, POs), and the form offers 0, 5, 12, 18 and 28. **SAC** is any 4–8 digit code; the form offers 9954, 9985 and 9987. **TDS nature** uses provisional keys in `contract-terms.ts` (`TDS_NATURES`: `contractor`, `professional`, `technical`, `rent_plant`, `rent_land`, `goods_purchase`) until CM-1116 brings finance's natures, which should adopt or map these keys. A new Work Order left without one gets `contractor` when the Contractor has TDS applicable, else none; an edit that leaves it out keeps it; null means no TDS.
- **Lines.** A BOQ line names a live BOQ item of the Project (400 `WORK_ORDER_BOQ_ITEM_INVALID`); its blanks come from the item (item no, description, UoM, SAC/HSN, the **current** rate) and its quantity defaults to what is left when that is more than 0, otherwise it must be typed. A non-BOQ line needs a description and UoM. 1–500 lines; quantity and rate as on the BOQ (four places; paise; amount ≤ ₹1,000 crore). A line sent back with its `id` keeps its id, **kind and BOQ item**; lines not sent are tombstoned (their ids stay valid for bills); positions follow the order sent.
- **Remaining quantity** = BOQ current quantity − Σ quantity on live lines of the Project's other live Work Orders that are **not cancelled** (closed ones still count). More than that is a **warning**, never a refusal: `warnings[]` (`WORK_ORDER_QUANTITY_OVER_REMAINING`, per BOQ item with this Work Order's lines added up, `ordered`, `remaining`, `message`) on create, update, amend and the detail of a draft, pending or issued Work Order. The form shows the same warning while you type.
- **Financial.** As CM-1103: without `contracts.work_orders` Financial every rate, amount, value, the mobilisation advance and the material issue and penal rates are `null`, and rates sent are ignored. A kept line keeps its rate, a new BOQ line takes the BOQ's current rate, a non-BOQ line ₹0; a kept advance stays; a new at-cost material takes the Material's unit rate. The form hides those fields and the total.
- **Materials issued** (CM-0023 §10). One row per Material (400 `WORK_ORDER_MATERIAL_DUPLICATE`), at most 100, an enabled Material (or one already on the Work Order). Issue basis free or at cost (an at-cost row needs its issue rate; a free one drops it), wastage 0–100 %, optional penal rate. Coefficients are per line, sent by the line's **index**; a line left out takes the Material's coefficient in the rate analysis of the line's BOQ item's library Item (several analysis lines of one Material add up), a blank one means none. The form prefills them when a Material is picked or a BOQ line added, and sends every one. Saving replaces the rows (new ids); an edit that leaves `materials` out keeps them, minus coefficients of removed lines. CM-1110 should key reconciliation on (Work Order, Material), not the row id.
- **Life and flags.** Draft → submit → pending approval → approve → **issued**, or reject (reason) → draft with `reject_reason` shown until resubmitted. Create needs Create; editing, submitting a draft: Update, or Create for its creator; deleting a draft: Delete, or Create for its creator; Approve and Reject their flags (the approval kernel's `approve`/`reject`; 409 `WORK_ORDER_NOT_PENDING` is checked first so the message names the real status; 400 `REJECTION_REASON_REQUIRED`); **close and cancel need Update**. Any other step in the wrong status is 409 `WORK_ORDER_STATUS_INVALID` (`details.status`, `details.action`). There is no Save & Approve; the approver may be the creator.
- **Amendment.** Update **and** Approve, a reason (400 `AMENDMENT_REASON_REQUIRED`), and the same form as an edit. **No second approval round**: the amender holds Approve, so it takes effect at once and stays issued. The revision row keeps the revision it replaced (`revision` = the old number) with **the reason it was amended**, and a JSON snapshot of the header, terms, lines (with UoM names), value and materials (with names), so an old revision reads the same after a master is renamed; the Work Order's `revision` goes up by one. A line on an **approved** bill (`bill_lines.work_order_line_id` on a live bill with status `approved`) cannot be removed (409 `WORK_ORDER_LINE_BILLED`, `details.lineId`) or cut below the billed quantity (409 `WORK_ORDER_QUANTITY_BELOW_BILLED`, `details.lineId`, `details.billed`). The detail shows each line's billed quantity.
- **Close and cancel.** Close an issued Work Order with a date on or after the order date (400 `CLOSED_ON_BEFORE_ORDER_DATE`) and a reason; refused while a live bill on it is draft or pending approval (409 `WORK_ORDER_BILL_OPEN`, `details.count`). The close date becomes the completion date (DLP start) when none was recorded. Cancel a draft or issued Work Order with a reason, dated the Company's today; refused once an approved bill names one of its lines (409 `WORK_ORDER_BILLED`: close it instead) or while a bill is open. A cancelled Work Order's lines stop counting against the BOQ.
- **Optimistic checks.** Update and amend need `expectedUpdatedAt`; delete, submit, approve, reject, close and cancel check it when sent (409 `WORK_ORDER_CHANGED`); the screens always send it.
- **One writer per Project.** Every Work Order command takes the BOQ's advisory lock (`construction_contracts.boq:{workspace}:{project}`), so Work Order and BOQ changes on a Project never cross: the remaining quantity and the BOQ delete guard read committed lines.
- **BOQ guard (CM-1103 follow-up).** A BOQ item named by a live line of a live, non-cancelled Work Order cannot be deleted: 409 `BOQ_ITEM_IN_WORK_ORDER`, `details.workOrders` (their numbers, “Draft” for one never submitted), checked inside the BOQ lock. The BOQ import never deletes items, so it needs no guard. Renumbering a BOQ item stays allowed: a Work Order line keeps its own copy of the item no. The BOQ's delete dialog says that an item a Work Order names cannot be deleted, and shows the server's message naming the Work Orders.
- **Notifications.** Submit, approve and reject dispatch `document.submitted|approved|rejected` with approval type `work_order` (`APPROVAL_DOCUMENTS`, menu `contracts.work_orders`, link to the detail page): messaging's `approval.requested` is the ticket's `work_order.pending_approval`, as with Variations. Approval also raises **`WorkOrderIssued`**, which messaging turns into **`work_order.issued`** (“Work Order WO/… is issued”, “To {Contractor} in {Project}.”) for Work Order Read + Notification holders on the Project, never the approver — the same kind of non-approval notice as `booking.created`. The menu already had the Notification flag (CRUDAJPNOF).
- **PDF.** `GET …/{id}/pdf` needs **Print**. The Purchase Order's page writer moved to `src/shared-kernel/pdf/document-pdf-writer.ts` (procurement re-exports it) so contracts can use it: A4, embedded Noto fonts, wrapped cells, a header that repeats on each page. It prints the Company letterhead, the Project (site address, state, Client), the number, revision, status and dates, the Contractor and Department (address, GSTIN / PAN), the scope note, the line table (item no, description, UoM, qty, rate, amount) with the total, the terms, the materials issued, and signature blocks for the Contractor and the Company. Without Financial it prints quantities only (no rates, amounts, total or advance amount). `?inline=1` opens it in the browser.
- **Audit.** `work_order.created|updated|deleted|submitted|approved|rejected|amended|closed|cancelled`; the amendment carries its reason. Snapshots hold the header, terms, line count and value.
- **Screens.** The list filters by status, Contractor (shown to Work Order editors, whose form options list the Contractors) and a search on number or scope; cards at phone width, a table above. The form has a header card, a terms card, the lines table (scrolls inside its frame) with **Add from BOQ** (a dialog with what each item has left, several at once) and **Add line**, the live warning, a running total, and the materials panel that opens on demand. The detail shows the status, actions behind their flags (Edit, Amend, Submit, Approve, Reject, More → Close / Cancel / Delete, Download PDF), the reject, close or cancel reason, the warnings, the terms, lines with billed quantities, materials and the revisions, each opening to its old terms and lines.
- **Not yet.** Backups (CM-907) do not include Work Orders yet, as with the BOQ. Advances themselves (CM-1108), bills (CM-1106), escalation (CM-1109) and reconciliation (CM-1110) build on these tables.

### CM-1105 — Measurement Book

- **Where it is.** Project → Contracts → **Measurements** (`/app/projects/{id}/measurements`), with `/new?side=client|contractor` and `/{sheetId}`. One page per sheet: a draft the viewer may change is edited in place; a submitted, checked or billed sheet reads only. `measurement.submitted` links to the sheet. The `measurements` stub left `CONTRACTS_MODULE_TICKETS`.
- **HTTP shape.** Everything is under `/api/construction/contracts/measurements`, Project-scoped like the BOQ and Work Orders: the list, create, `form-options` and `quantities` name the Project, and a sheet is reached by its id (`/{id}`, `/{id}/update|delete|submit|check|return|reopen`, `/{id}/photos/**`). Access is checked first (403 `PERMISSION_DENIED`, then 404 `PROJECT_NOT_FOUND`); another Company's sheet is 404 `MEASUREMENT_NOT_FOUND`. Every step answers with the whole sheet, its rows, the cumulative panel and `allowed` (what the caller may do now).
- **Menu Notification flag.** `contracts.measurements` is **CRUDAPNO** (ADR CM-0023 §6 updated), so a submitted sheet reaches the holders of Approve + Notification. The seeded Admin and Project Manager templates hold it, in `designations.json` and in the unshipped M11 menus migration (`20261021090500`, edited in place as CM-1103 did). Both M11 databases had recorded an older checksum for that migration (before CM-1103's edit): the grants SQL was run again (it only ORs bits, so it is idempotent) and `_prisma_migrations.checksum` was set to the file's SHA-256, so `migrate deploy` is clean on `construction_m11` and `construction_test_m11`.
- **Sides.** A sheet's side and Work Order are fixed when it is created (delete the draft to start again). The **client side** measures live BOQ items of the Project and names no Work Order (400 `MEASUREMENT_WORK_ORDER_NOT_ALLOWED`). It is allowed on **Own development** Projects too: there the BOQ is a budget and is never billed, but measuring it tracks progress, and checked rows lock BOQ items just the same. The **contractor side** needs one Work Order of the Project that is **issued** (400 `MEASUREMENT_WORK_ORDER_REQUIRED` / `MEASUREMENT_WORK_ORDER_INVALID`), checked on create, edit, submit and check; its rows name live lines of that Work Order. A row naming the other side's item, or a line of another Work Order, is 400 `MEASUREMENT_ITEM_INVALID` with `details.row` and `details.field` (`rows.N.boqItemId` / `rows.N.workOrderLineId`).
- **The quantity rule.** `quantity = nos × (the product of the filled dimensions)`. Length, breadth and depth/height may each be blank (left out, not 0); a blank nos is 1, so nos alone counts pieces. Every number has at most four decimals; the product is rounded **once**, half up (away from zero for a deduction), to four decimals — never per factor. A row may instead be **direct**: the quantity is typed and nos and the dimensions are dropped. Dimensions are more than 0, nos is not 0, a direct quantity is not 0, and a row that works out to 0.0000 is refused (`MEASUREMENT_DIMENSION_INVALID`, `MEASUREMENT_NOS_INVALID`, `MEASUREMENT_QUANTITY_INVALID`, `MEASUREMENT_QUANTITY_ZERO`). |quantity| stays below 10¹² (`DECIMAL(16,4)`).
- **Deductions** are a **negative nos** (or a negative direct quantity), not a toggle: one number carries the sign, nothing new is stored, and a deduction row reads as "−1 × 0.9 × 2.1". Screens mark it "Deduction".
- **Rows.** At most 500 a sheet; a description of at most 500; an optional `LocationRef` checked by the Project's location resolver (errors carry `details.row`). Saving a draft replaces its rows (new ids): nothing points at a draft's rows. The form is the site-work location picker in a dialog per row.
- **Header.** Measured on (not in the future, 400 `MEASURED_ON_IN_FUTURE`), a title (≤ 120) and remarks (≤ 2,000, line breaks kept).
- **Back-dated entry.** Module `measurement` ("Measurement Book", the Contracts group, entry date `measuredOn`, menu `contracts.measurements`). A create checks the date measured; an edit checks the stored date and, when it changes, the new one. Submit, check, return, reopen and delete are not date edits.
- **Life and flags.** Draft → submit → **submitted** → check → **checked**. Create needs Create. Editing and submitting a draft: its creator with Create, or Update. Submit needs at least one row (400 `MEASUREMENT_ROWS_REQUIRED`). **Check, return and reopen need Approve** (403 otherwise); the checker may be the drafter. Any step in the wrong status is 409 `MEASUREMENT_STATUS_INVALID` (`details.status`, `details.action`). **Delete** is allowed in any status: a draft by its creator with Create or a Delete holder, a submitted or checked sheet by a Delete holder only (a tombstone; a checked one stops counting as measured).
- **Check (the joint measurement).** Records `checked_by` = the caller (our engineer), `checked_at`, and the other party's `party_name` (≤ 120) and `party_role` (≤ 80), both required, and `joint_on`: required, on or after the date measured (400 `JOINT_ON_BEFORE_MEASURED_ON`) and not after the Company's today (400 `JOINT_ON_IN_FUTURE`).
- **Return and reopen.** Return sends a submitted sheet back to draft with a reason (400 `RETURN_REASON_REQUIRED`, ≤ 500), clearing who submitted it. Reopen sends a checked sheet back to submitted with a reason (400 `REOPEN_REASON_REQUIRED`) and **clears the joint measurement** (checker, party, date — the audit keeps them), so its rows stop counting as measured until it is checked again. The reasons had no columns: migration `20261022120000_construction_contracts_measurement_photos` adds `return_reason` and `reopen_reason` to `measurement_sheets`; each is shown until the sheet is submitted (return) or checked (reopen) again.
- **Billed is read-only.** Once any row has a `bill_id`, edit, submit, delete, check, return, reopen and photo changes are refused with 409 `MEASUREMENT_BILLED` (`details.count`), checked before the status so the message names the real reason. CM-1106 sets and clears `bill_id`; the tests set it directly.
- **One writer per Project.** Every Measurement Book command (both sides, photos too) takes the BOQ's advisory lock (`construction_contracts.boq:{workspace}:{project}`), so a check, reopen or delete and a BOQ edit or Work Order change never cross. The HTTP test shows CM-1103's `BOQ_ITEM_MEASURED` tripping from a real checked sheet and clearing on reopen. Optimistic `updatedAt` on every change: update needs `expectedUpdatedAt`; the other steps check it when sent (409 `MEASUREMENT_CHANGED`); the screens always send it.
- **Cumulative and deviation.** Per item of a sheet: `checked` = Σ rows on the Project's **other** live checked sheets of that side naming it, `thisSheet` = Σ this sheet's rows (whatever its status), `total` = the two, against `planned` = the BOQ item's **current** quantity (client) or the Work Order line's quantity (contractor). `over` when total > planned. A row is marked `over` (shown as "Deviation" / "Over WO") when, walking the sheet's rows in order from `checked`, it adds to the item (not a deduction) and the running total after it is above planned. Client side: `overLimit` when the total is beyond the Company's deviation limit (`isDeviation`, CM-1103), with the % over (two places, half up) and a link to the BOQ's Deviations tab (which lists checked quantities only). Contractor side: no limit; each over line is a warning naming 409 `WORK_ORDER_QUANTITY_EXCEEDED`, which CM-1106 will raise when a bill takes more than the Work Order holds — amend the Work Order first.
- **Quantities read.** `GET …/measurements/quantities?projectId&side[&workOrderId]` (Read) lists every live BOQ item, or every live line of one Work Order, with `checked` (live checked sheets) and `pending` (submitted, not yet checked), and the same marks. The form adds its rows to `checked` in the browser with the same domain functions, so the marks move while you type.
- **Form options.** `GET …/form-options` (Create or Update) answers the Project's role and structure, the Client's name, the BOQ's live items in section order with their current quantity, and the **issued** Work Orders (up to 500) with their live lines.
- **Photos.** Through the attachments service (CM-0014) like a Daily Worksheet's: images only (PNG, JPEG, WebP), 25 MB each, 20 a sheet (409 `DOCUMENT_FILES_LIMIT`), WebP thumbnails, `stored_files` kind `measurement_photo`, keys under `measurement-photos/<sheetId>`. They are kept in the new `construction_contracts.measurement_photos` table and **not** indexed in the Project Gallery (the sheet is evidence for a bill, not site progress). Read sees them; Create or Update adds them; Update removes any, Create only one's own; none of it once billed.
- **Notifications.** Submit raises **`MeasurementSubmitted`** after commit; messaging turns it into **`measurement.submitted`** ("Measurement sheet of 20/10/2026 is ready to check", the side, party, title and row count) for Measurement Book **Approve** + Notification holders on the Project, never the submitter — like CM-1104's `work_order.issued`. Check, return and reopen send no notice yet.
- **Audit.** `measurement_sheet.created|updated|deleted|submitted|checked|returned|reopened` (return and reopen carry the reason), `measurement_photo.added|removed`. Snapshots hold the side, Work Order, date, status, title, the joint measurement, the row count and the total quantity.
- **Screens.** The list filters by side, status and (for editors, whose form options list them) Work Order; cards at phone width, a table above. A sheet shows its status and actions by `allowed` (Submit for checking, Check, Return to draft, Reopen, Delete), the return or reopen reason, the over-Work-Order warning, then the rows — while a draft, as a form whose rows show their quantity as you type, with add, duplicate and remove, a searchable item picker and a per-row location dialog — the "Measured to date" panel and the photos. Check opens a dialog for the other party's name, role and the date. At 375 px each row is a card with nos, L, B and D/H in a 2×2 grid, and nothing scrolls sideways.
- **Submit never sends stale rows.** While a draft is edited on its page, Submit lives in the form, not the page header. With unsaved changes it reads "Save and submit for checking": it saves first and submits only when that save succeeds, sending the saved sheet's new `updatedAt`. A failed save (a 400 under its field, or 409 `MEASUREMENT_CHANGED`) stops it there. Check, return and reopen act on submitted or checked sheets, which are never shown as an editable form, so they need no such guard. Delete removes the sheet with any unsaved changes.
- **No quantities before a Work Order.** A new contractor-side sheet asks `…/quantities` only once a Work Order is picked (the query is disabled until then). Until then the "Measured to date" panel says to pick the Work Order.
- **Not yet.** Backups (CM-907) do not include the Measurement Book yet, as with the BOQ and Work Orders. A BOQ item or Work Order line named only by draft or submitted rows can still be deleted or amended away; such a row then fails its next save (400 `MEASUREMENT_ITEM_INVALID`) and shows "Item removed". No PDF of a sheet yet (the bill PDF's measurement detail is CM-1106/CM-1107).

### CM-1106 — Contractor bills

- **Where it is.** Project → Contracts → **Contractor Bills** (`/app/projects/{id}/contractor-bills`, `?workOrderId=` filters to one Work Order) and `/{billId}`. "New bill" is a dialog, not a page: it needs only the Work Order and two dates. Approval notices and finance's invoice sheet link to the bill page. A Work Order's page shows "Contractor bills: N bills" (only to those who may read bills). The `contractor_bills` stub left `CONTRACTS_MODULE_TICKETS`.
- **HTTP shape.** Everything is under `/api/construction/contracts/contractor-bills`, Project-scoped like Work Orders: the list, create and `form-options` name the Project, and a bill is reached by its id (`/{id}`, `/{id}/update|refresh|delete|submit|approve|reject|reverse`, `/{id}/suggestions`, `/{id}/pdf`). Access first (403 `PERMISSION_DENIED`, then 404 `PROJECT_NOT_FOUND`); another Company's bill is 404 `BILL_NOT_FOUND`. Every step answers with the whole bill and `allowed` (what the caller may do now).
- **Draft.** A draft names one **issued** Work Order of the Project (400 `BILL_WORK_ORDER_INVALID`) and takes every row of its live, **checked** contractor-side sheets measured on or before "measured up to" that no bill has taken (`bill_id` null), setting `bill_id` in the same transaction under the Project's BOQ lock. No rows: 400 `BILL_NO_MEASUREMENTS`. The bill is inserted before anything is measured, so a second open bill on the Work Order is refused by the partial index first (409 `BILL_OPEN_EXISTS`).
- **Dates.** The bill date is not after the Company's today (400 `BILL_DATE_IN_FUTURE`) and not before the Work Order's date (400 `BILL_DATE_BEFORE_ORDER_DATE`); "measured up to" is not after the bill date (400 `MEASURED_UP_TO_AFTER_BILL_DATE`). **Back-dated entry:** module `contractor_bill` ("Contractor Bill", Contracts group, entry date `billDate`, menu `contracts.contractor_bills`): a create checks the bill date, an edit the stored date and a new one. Refresh, submit, approve, reject, reverse and delete are not date edits.
- **Number and ordinal.** A draft has neither (screens show "Draft"); migration `20261022150000_construction_contracts_bill_number_nullable` makes both nullable (the live-number and ordinal partial indexes ignore nulls). The first submit takes the number from the `contractor_bill` sequence rule for the Project, dated the bill date, and the ordinal = the highest ordinal among the Work Order's live bills that are not rejected or reversed + 1. A rejected bill keeps its number, and the next bill reuses its ordinal (RA 1 again).
- **The abstract.** One line per Work Order line with rows, in the Work Order's line order: this bill = Σ its rows (deduction rows included), previous = Σ the line on earlier **approved** bills (`bill_lines`), cumulative = previous + this, amount = round(cumulative × rate) − round(previous × rate), half up, in `bigint`. Gross = Σ amounts = cumulative value − previous value, so two bills always add up to the cumulative value to the paisa.
- **Which rate.** The Work Order line's rate when the bill is drafted or refreshed, stored on the bill line. After an amendment changes a rate, the next bill re-values the previous quantity at the new rate (cumulative and previous both at it), so earlier bills are never reopened and the difference is billed only on new quantity. A pending bill keeps the rate it was drafted with; to take a new rate, reject it and draft again.
- **Within the Work Order.** 409 `WORK_ORDER_QUANTITY_EXCEEDED` (`details.lineId`, `cumulative`, `workOrderQuantity`) when a line's cumulative is above its Work Order quantity, or the line was removed by an amendment (quantity 0), on **draft, update with a new date, refresh, submit and approve** (an amendment may cut a line while a bill waits).
- **Refresh and update.** Refresh frees the draft's rows and takes them again, up to its date or a new one, at the Work Order's rates and terms now. An update takes the dates, remarks, Final flag and (with Financial) the deductions; a new "measured up to" re-takes the rows like a refresh, otherwise the abstract and GST stay. Deductions left out are kept. Delete (a tombstone), reject and reverse free the rows.
- **Retention.** Suggested = gross × the Work Order's retention %, half up, cut so the retention on the Work Order's **approved** bills never passes cap % × the Work Order's value (its current revision). Releases do not make room under the cap: it limits what is deducted over the contract. The suggestion is also the most a bill may hold (400 `BILL_RETENTION_OVER_CAP`, `details.max`); it can be edited down. A new draft holds the suggestion; on a refresh, retention left at the old suggestion follows the new one, and typed retention stays, cut to the new maximum.
- **Other deductions.** Typed, each with an amount (> ₹0, paise) and an optional description (≤ 200): mobilisation advance recovery (manual until advances exist; `bill_deductions.advance_id` and `GET …/suggestions`' `mobilisationRecovery: null` are the CM-1108 hooks), material issued at cost, and other (the reason is required, 400 `BILL_DEDUCTION_REASON_REQUIRED`). Secured advance and material reconciliation recoveries are refused (400 `BILL_DEDUCTION_KIND_INVALID`) until CM-1108 and CM-1110. At most 20. All deductions together are at most gross + GST payable (400 `BILL_DEDUCTIONS_TOO_LARGE`), so the net is never negative. Without Financial, deductions sent are ignored.
- **GST.** From the Work Order's terms: SAC, rate (none: no GST) and reverse charge, copied onto the bill. The supplier state is the Contractor's `state_code` and the place of supply the Project's state (works on immovable property, CM-0023 §11). Same state, or either unknown, is intra-state, as procurement treats it (`defaultSupplyType`); CGST + SGST is split by the shared `splitGst`, CGST taking the odd paisa; different states are IGST. GST is rounded once on the gross. The supplier GSTIN is copied; the recipient (Company) GSTIN stays null until CM-1113.
- **Reverse charge.** The GST is worked out and shown (and kept in `cgst`/`sgst`/`igst`), but the Company pays it, so `payableGst` is 0 and net = gross − deductions. The bill and the PDF show it and take it back out.
- **Net.** gross + GST payable − deductions.
- **Submit and decide.** Submit (the creator with Create, or Update) checks the abstract again and needs a gross above ₹0 (409 `BILL_GROSS_NOT_POSITIVE`). Approve and Reject use the approval kernel (409 `BILL_NOT_PENDING`, 400 `REJECTION_REASON_REQUIRED`) with their flags and raise `document.submitted|approved|rejected` with document type `contractor_bill` (`APPROVAL_DOCUMENTS`, menu `contracts.contractor_bills`, link to the bill page). There is no Save & Approve; the approver may be the drafter. Any other step in the wrong status is 409 `BILL_STATUS_INVALID`. Optimistic `updatedAt`: update needs `expectedUpdatedAt`; the other steps check it when sent (409 `BILL_CHANGED`).
- **Final bill.** "Final" is a flag on the draft. Approving a Final bill that leaves any Work Order line below its quantity (earlier approved bills + this one) is refused with 409 `BILL_FINAL_UNBILLED` and `details.lines` (line, item no, billed, Work Order quantity); the bill page shows them and "Approve and close" sends `confirmUnbilled: true`. Approval then closes the Work Order through the Work Order store, under the same lock: status closed, `closed_on` = the bill date, the reason "Final bill CB/… approved.", and the completion date (DLP start) when none was recorded; audited as `work_order.closed`.
- **Reverse.** An approved bill is reversed with a reason and **Approve** (400 `REVERSE_REASON_REQUIRED`): only while no other live bill on its Work Order is open (draft or pending) or approved with a higher ordinal (409 `BILL_NOT_LATEST`: reverse or delete the later ones first, so a draft's previous quantities never go stale), and while its invoice has no live payment allocation, no write-off and no settlement pending or approved (409 `BILL_SETTLED`, asked through `PartyInvoicing.isSettled`). Finance then reverses the invoice's party entry and tombstones the invoice, the rows are freed, and the bill is `reversed` (kept, with who, when and why). A reversed **Final** bill reopens its Work Order: issued again, `closed_on`, the close reason and the completion date cleared (only a Final bill closes a Work Order that billing reopens, and a closed Work Order cannot be amended, so nothing else changed it), audited as `work_order.reopened`.
- **Finance: `PartyInvoicing`.** Implemented in `src/composition/contracts-party-invoicing.ts` over finance's own `ContractorBillInvoices` (`src/finance/application/contractor-bill-invoices.ts`), inside the bill's transaction, so the bill and its invoice commit together; contracts never writes finance tables. Migration `20261022150100_construction_finance_ra_bill_origin` adds the origin `ra_bill`, `invoices.source_id` (the bill) and widens `invoices_figures_check` (an `ra_bill` invoice is a Contractor's, payable, with a source; it compares the origin as text, because a new enum value cannot be used as a literal in the transaction that adds it). The migration was edited in place before shipping, re-applied and re-checksummed on `construction_m11` and `construction_test_m11`.
- **The invoice.** A payable Contractor invoice on the bill's Project: number = the bill number (409 `BILL_INVOICE_NUMBER_TAKEN` when the Contractor already has a live payable invoice with it, which only a per-Project rule without a project token or a hand-typed invoice can cause), date = the bill date, no due date, the Department from the Work Order, **taxable = gross, GST = the GST payable** (CGST + SGST + IGST; 0 under reverse charge, so the TDS base finance works out at payment is not cut by GST nobody pays the Contractor) in finance's one `gst_amount` until CM-1113 splits it, and **amount = the bill's net** (retention and recoveries taken off). Its one party-ledger entry is `invoice` = net. A bill whose net is ₹0 creates no invoice. The bill stores the invoice id in `bills.invoice_id`. Audited `invoice.created_from_contractor_bill` and `invoice.reversed_with_contractor_bill`.
- **Read-only in finance.** An `ra_bill` invoice cannot be edited or deleted there (409 `INVOICE_FROM_CONTRACTOR_BILL`, and `actions.edit`/`delete` are false); payments, allocations and settlements work as on any invoice. The invoice response carries `origin` and `sourceId`, and the invoice sheet says "From Contractor Bill CB/…" with a link to the bill.
- **Retention held: derived in contracts.** CM-0023 §7 asked for a `retention_held` party-ledger entry kind. Finance sums `party_entries` without a kind filter in at least seven places: `partyLedger.balances`, the store's `kindTotals`, `balanceBefore` and `balancesByProject` (balances, statements, the dashboard), the central payment's workspace balances, the due/ageing invoices, the finance report source's party summary, and the backups export them as they are. A new kind would silently change every one of those balances, so retention held is instead **derived in contracts**: Σ retention deductions on approved, unreversed bills (− releases, which CM-1108 adds). The finance invoice is only what is payable now; CM-1108's release creates the payable for what it releases. "Retention held" shows per Contractor on the Contractor Bills page (Financial) and per Work Order on each bill. ADR CM-0023 §7 was amended to say so. Existing finance HTTP tests are unchanged and pass: no balance moves except by an `ra_bill` invoice.
- **TDS estimate.** Not a deduction (CM-0017): the bill page and PDF show "TDS estimate (194C or 393 (194C)) at r % of the gross: about ₹x", with "Estimate only: TDS is deducted when the bill is paid, on that payment's figures." The rate is the 194C row in force on the bill date for the Contractor's payee kind (from the PAN), or its lower-deduction certificate's; thresholds and the year's earlier payments are left out. It reads finance's TDS table through a `ContractorTdsEstimator` port wired in `src/composition`. Null without Financial.
- **Financial.** Without `contracts.contractor_bills` Financial every rate, amount, value, GST, deduction amount, net, total, retention figure and the TDS estimate is `null`; the list has no totals or retention held; the page and PDF show quantities (and the deduction kinds) only.
- **List.** Newest first; filters by status, Work Order, Contractor and bill date range; cursor pages. **Totals** (count, gross, GST, deductions, net) are over the bills the filter matches that count — draft, pending and approved, not rejected or reversed. `form-options` (Create) lists the issued Work Orders with their unbilled checked rows per date measured and any open bill, so the dialog counts the rows a date takes in the browser and links to the open bill.
- **PDF.** `GET …/{id}/pdf` (Print) reuses the shared page writer: the letterhead, the Project and Contractor, the bill and RA numbers and dates, then the three parts — the **abstract** (item, description, UoM, rate, previous / this / cumulative and amount, then value to date, less previous bills, gross), the **measurement detail** per line (date, description, location, nos, L, B, D/H, quantity), and the **deductions, GST and net** with the TDS estimate note — remarks, and signature blocks for the measuring engineer, the Contractor and the Company. "Final Bill" or "Running Account Bill" heads it. Quantities only without Financial.
- **Locations.** A row's `LocationRef` is labelled ("Wing A · Ground Floor") with the projects context's names through a `locationLabels` port (`projectLocationLabeller`), for the page and the PDF.
- **Audit.** `contractor_bill.created|updated|refreshed|deleted|submitted|approved|rejected|reversed` (reject and reverse carry the reason, delete/reject/reverse the rows freed), plus `work_order.closed|reopened` and finance's own invoice events. Snapshots hold the number, ordinal, status, Work Order, dates, Final, gross, GST, reverse charge, deductions, net and the invoice.
- **Screens.** The list (filters, totals, retention held, cards at phone width). The bill page: status and actions by `allowed` (Download PDF, Refresh measurements, Submit for approval, Approve, Reject, More → Reverse bill / Delete draft), the reject or reverse reason, the invoice in Payments once approved, the facts, the **abstract** as one card per line with previous / this / cumulative (of the Work Order quantity) and a "Show N measurements" toggle listing the rows with their working (nos × L × B × D), the draft's **Bill details** form (dates, Final, remarks, the deductions editor with "Use suggested retention" and the net as typed), and **GST and net** with the TDS estimate and the retention held on the Work Order. Dialogs: reject, reverse, the Final confirm and delete. At 375 px everything is cards and nothing scrolls sideways.
- **Not yet.** Backups (CM-907) do not include contracts bills yet, as with the rest of contracts. Notifications other than the approval ones (e.g. "bill approved" to the Contractor's contact) are not sent. Advances and their recovery suggestions (CM-1108), material reconciliation recovery (CM-1110), the GST split on finance invoices and the recipient GSTIN (CM-1113) and TDS natures beyond 194C (CM-1116) build on these hooks.

### CM-1107 — Client bills

- **Where it is.** Project → Contracts → **Client Bills** (`/app/projects/{id}/client-bills`) and `/{billId}`. "New bill" is a dialog with the bill date and "measured up to", counting the checked client-side rows the date takes and linking to a bill already open. The page also holds the **client contract terms** (below the list, edited in a dialog). Approval notices and finance's invoice sheet link to the bill page. The `client_bills` stub left `CONTRACTS_MODULE_TICKETS`, which is now empty.
- **One engine, two sides.** The parts both sides use moved out of `contractor-bill.ts` into `src/contracts/domain/ra-bill.ts`: the header and dates, line maths (`lineFigures`: round(cumulative × rate) − round(previous × rate)), `billValues`, `sumRowsBy`, the retention suggestion and cap (`raRetentionSuggestion` against a "contract value"), GST (`billGst`, `storedBillGst`), deductions (`raBillDeductions` with the side's kinds), `assertRaDeductions`, the net, the life (`assertBillAction`, `billActions`, `reverseReason`) and the shared errors. `contractor-bill.ts` keeps its names on top of it. The application steps both sides share are in `ra-bill-common.ts` (stale check, approval state, `document.*` event, the deduction plan where retention left at the suggestion follows the gross, the audit snapshot); the Prisma bill columns, deductions, tombstone, row take/free, measurement-row mapping and paging in `prisma-ra-bill-rows.ts`; the PDF letterhead, abstract, value totals, measurement detail, GST rows, deductions and signatures in `ra-bill-pdf-parts.ts`. Contractor Bills use all four; their tests are unchanged and pass.
- **Which Projects.** A Client Bill needs a **Contract work** Project (400 `PROJECT_NOT_CONTRACT_WORK`), a linked Client (400 `PROJECT_CLIENT_REQUIRED`) and a state (400 `PROJECT_STATE_REQUIRED`), checked on create, a remeasuring update and refresh. The list and the dialog's form options answer `setup.blockers` in that order; the page shows the first as an empty state with a link to the Project's form ("Change the Project's role", "Pick the Client", "Set the Project's state") and names the rest.
- **Draft.** Takes every row of the Project's live, **checked** client-side sheets measured on or before "measured up to" that no bill has taken, under the BOQ lock; none is 400 `BILL_NO_MEASUREMENTS`. One open (draft or pending) running client bill per Project: the CM-1101 partial index refuses a second (409 `BILL_OPEN_EXISTS`). The bill stores the Project's Client when drafted (`bills.client_id`); a refresh or remeasure takes the Project's Client then.
- **Lines and rate.** One line per BOQ item with rows, in BOQ order (section position, then item position): previous = Σ the item on earlier **approved** client bills, at the BOQ item's **current rate** when drafted or refreshed (stored on the line), as CM-1106 does with the Work Order rate. Dates: not after the Company's today; "measured up to" not after the bill date; there is no earliest date on the client side.
- **Deviation, not refusal.** The client side may go past the BOQ quantity (ADR §4). Nothing is refused; each line carries `deviation` (`over`, `overBy`, `percentOver`, and `overLimit` against the Company's deviation limit, CM-1103). The page marks it "Deviation" (red past the limit, "needs a Variation") and the PDF prints a note under the line.
- **Client contract terms.** The one `client_contracts` row per Project, edited on the **Client Bills page** (Client Bill Update; 409 `CLIENT_CONTRACT_CHANGED` when stale): retention % per bill, the cap (% of the **BOQ's current value**), the share released at completion, DLP months, the handover date (where the client side's DLP starts, CM-1108), SAC and GST rate. They are checked with the Work Order's rules (`terms.*` errors). No row yet means no retention and no GST: the editor says so. Bills drafted or refreshed afterwards use them; a pending bill keeps what it was drafted with. Audited `client_contract.updated`.
- **Retention and deductions.** As CM-1106: suggested = gross × retention %, cut so retention on the Project's approved client bills never passes cap % × the BOQ value; also the most a bill may hold (400 `BILL_RETENTION_OVER_CAP`). The kinds are retention, mobilisation advance recovery (manual; `GET …/suggestions` answers `mobilisationRecovery: null`, the CM-1108 hook), material issued at cost, and other with a reason. Deductions are at most gross + GST.
- **A tax invoice.** Place of supply = the Project's state. Supplier GSTIN = the Company billing address in that state with a GSTIN, else the default billing address (else the first); when no address in the state has a GSTIN the bill carries the **warning** `GSTIN_NOT_IN_STATE` (shown on the page and the PDF, never an error). Recipient GSTIN = the Client's. CGST + SGST when the supplier GSTIN's state is the place of supply, else IGST (`splitGst`, CGST takes the odd paisa). Reverse charge never applies: `reverse_charge` stays false and is not shown. `supplier_gstin`, `recipient_gstin` and `place_of_supply_state_code` are stored on the bill when drafted or refreshed; an update that does not remeasure keeps them.
- **Number, approval and Final.** First submit takes the number from the `client_bill` sequence rule (prefix RA) for the Project, dated the bill date, and the ordinal = the highest among the Project's live client bills not rejected or reversed + 1. Approve and Reject use the approval kernel with document type `client_bill` (`APPROVAL_DOCUMENTS`, menu `contracts.client_bills`, link to the bill page). Back-dated module `client_bill` ("Client Bill", Contracts group, entry date `billDate`). **Final** marks the contract's final bill: the PDF heads its RA number "(Final bill)". Nothing closes on the client side (a BOQ has no status) and later bills are not refused; CM-1108 reads the handover date, not the flag, for the DLP.
- **The receivable invoice.** Approval creates it through `PartyInvoicing` (now both ways): origin `ra_bill`, direction `receivable`, party type `client`, the bill as `source_id`, number and date the bill's, no due date, **taxable = gross, GST = CGST + SGST + IGST in `gst_amount`** (one total until CM-1113 splits it), **amount = net** = gross + GST − the retention and recoveries the Client holds back. Its one party entry is `sales_invoice` −net. Net ₹0 creates none. Finance's `ContractorBillInvoices` became `RaBillInvoices` for both sides (`invoice.created_from_client_bill`, `invoice.reversed_with_client_bill`). In finance it is read-only (409 `INVOICE_FROM_CLIENT_BILL`; the guard is shared with `INVOICE_FROM_CONTRACTOR_BILL`) and the sheet says "From Client Bill RA/…" with a link. Manual invoices to a Client are refused (400 `CLIENT_INVOICES_FROM_CLIENT_BILLS`).
- **Reverse.** Approve; only while no other live client bill on the Project is open or approved with a higher ordinal (409 `BILL_NOT_LATEST`) and nothing is received, written off or pending write-off against the invoice (409 `BILL_SETTLED`). Finance reverses the entry and tombstones the invoice; the rows are freed.
- **Retention receivable: derived in contracts.** Like CM-1106's retention held, never a party entry: Σ retention deductions on approved, unreversed client bills (− releases, CM-1108). It shows on the Client Bills list (totals), each bill, the terms panel, and finance's Client balance, which reads it through the `ClientRetentionReceivable` port (`retentionReceivable` in `PartyFinanceDeps`, implemented in `src/composition/contracts-client-retention.ts`); finance does not import contracts. The ticket line and ADR CM-0023 §7 were amended to say so.
- **Finance party type `client`.** Migration `20261022180000_construction_finance_client_party` adds `client` to `party_type` and `counterparty_kind`, the party entry kinds `client_tds` and `gst_tds`, `party_payments.client_tds_amount` and `gst_tds_amount` (BIGINT, default 0), and widens the checks: a Client's invoices are receivable (and `ra_bill` may be a Client's receivable), Payment In is from an Other Party or a Client and a Client is never paid, the Client's deductions only on a Client's Payment In, and `client_tds`/`gst_tds` entries are positive (compared as text: new enum values cannot be literals in the transaction that adds them). It was edited in place before shipping, re-applied and re-checksummed on `construction_m11` and `construction_test_m11`. `PartyType`, `PARTY_TYPES`, `PARTY_TYPE_LABELS`, the API models, balances, statements, workspace balances, Central Payment (a Clients tab whose dues are receivable), dues and ageing, the Due Payments report, openings, settlements, Transactions' and petty cash's Paid To / Received From, and the backups (names from `construction_masters.clients`; the two new payment columns) all take Clients. A Client is "on" the Projects that link it: receipts elsewhere are 400 `PARTY_NOT_ON_PROJECT`.
- **Receipts from Clients with deductions.** A Payment In from a Client records **TDS deducted by the client** (`clientTdsAmount`; 194C, or 393 under the 2025 Act) and **GST-TDS** (`gstTdsAmount`; s.51, 2 % for government clients). Payment Out to a Client is 400 `PAYMENT_OUT_NOT_FOR_CLIENTS`; either amount on any other payment is 400 `CLIENT_TDS_ONLY_FOR_CLIENTS`. **Why new entry kinds rather than the existing `tds`:** the existing `tds` kind is the Company's own 194C deduction on a payment _out_ (negative, it lowers what the Company owes); the TDS ledger and Form 26Q work read `party_payments.tds_amount` for Contractors, the finance report source sums `kind = 'tds'` as TDS deducted, and the balance rows show it as such. A Client's TDS is the opposite: deducted _from_ the Company, a receivable to claim against Form 26AS, and GST-TDS must be told apart from it. So each gets its own column on the payment and its own positive party entry (`client_tds`, `gst_tds`), posted beside `receipt` +cash. **Allocation reuses the existing rule:** a payment's settled amount is what moved plus what was deducted (`settledAmount` = amount + TDS + client TDS + GST-TDS), allocations may take up to it, so the invoice's balance falls by cash + TDS + GST-TDS and it shows Paid; the account moves only by the cash (`counterparty_kind = client`). The same sum replaced `amount + tds_amount` in the store's advances, Central Payment and `tdsShare`. Other parties' payments have zeros there, so no other balance moves: the finance HTTP suite is unchanged except Central Payment's response gaining `parties.client`.
- **The Client's balance.** Finance's party balances answer `clientTds`, `gstTds` and `retentionReceivable` beside the existing figures (0 for other parties). The Clients tab shows Invoiced, Received, TDS receivable, GST-TDS receivable, Written off, **Due** (the balance turned round: what the Client owes), Overdue and Retention receivable; the Client's page adds a "Client receivables" panel (due, retention, TDS and GST-TDS receivable) and only "Receive payment" (no New invoice). The receipt form shows the two deduction fields for Clients only, with "Settles ₹x: received + TDS + GST-TDS"; the payment page and the receipt PDF list them.
- **PDF.** `GET …/{id}/pdf` (Print) is a **Tax Invoice**: the letterhead with the supplier billing address and GSTIN, the invoice number and date, place of supply (state name and code), SAC, RA number, "Reverse charge: No"; supplier and recipient blocks (name, address, GSTIN, state; the Client's PIN); the `GSTIN_NOT_IN_STATE` warning; the abstract with deviation notes and the measurement detail; taxable value, CGST/SGST or IGST with rates, the invoice value and its amount in words; deductions, the net receivable and its amount in words; signatures for the measuring engineer, the Client and the Company. Quantities only without Financial. Amount in words moved from procurement to `src/shared-kernel/amount-in-words.ts` (Indian numbering; it ends "… Only", as the Purchase Order and party receipt print it).
- **Audit.** `client_bill.created|updated|refreshed|deleted|submitted|approved|rejected|reversed` (snapshots add the Client, place of supply and both GSTINs), `client_contract.updated`, and finance's invoice events.
- **Not yet.** The GST split on finance invoices (CM-1113), e-invoice JSON (CM-1113), the Client's advances and retention release (CM-1108), the TDS receivable register and Form 26AS reconciliation (CM-1117), and backups of contracts bills remain. The Project Dashboard's due widgets read payables only, so client dues show in Central Payment and the Due Payments report, not there.

### CM-1108 — Advances, retention release, DLP

- **Where it is.** No page of its own: four panels — **Advances given** (or **received**), **Retention held** (or **receivable**), **Bank guarantees** and **Defects liability period (DLP)** — sit on an issued or closed Work Order's page (contractor side) and below the client contract terms on the Client Bills page (client side). They are cards at every width (two columns from `lg`). The bill editors show **Advance recoveries** (each advance, what is left, what the gross suggests, "Use") and a recovery row picks its advance. Finance's invoice sheet says "From retention release on WO/… / the client contract" with a link, and its lists mark "(retention release)".
- **HTTP shape.** Reads where the panels show: `GET …/work-orders/{id}/advances-retention` (Work Order Read) and `GET …/client-bills/contract/advances-retention?projectId=` (Client Bills Read). Writes in three sibling areas whose body names the contract by `projectId` and, on the contractor side, `workOrderId` (none means the Project's client contract): `POST …/advances`, `…/advances/{id}/update|delete`; `POST …/guarantees`, `…/guarantees/{id}/update|release|delete`; `POST …/retention-releases`, `…/retention-releases/{id}/delete`; and `POST …/work-orders/{id}/completion`. Access first (403 for the side's menu; then 404 `PROJECT_NOT_FOUND` / `WORK_ORDER_NOT_FOUND`); a record of another Company is its own 404 (`ADVANCE_NOT_FOUND`, `GUARANTEE_NOT_FOUND`, `RETENTION_RELEASE_NOT_FOUND`). Every write answers the contract's whole view, like bills answer the whole bill.
- **Permissions.** The contractor side is `contracts.work_orders`, the client side `contracts.client_bills`: Read sees, **Update** records and edits (and needs **Financial** for anything with an amount: 403 without), **Delete** deletes, **Approve** releases DLP-end retention before the DLP ends, Financial shows money (null without). Recording an advance also needs finance **Parties Create** on the Project and deleting one Parties **Delete**: the advance's payment goes through finance's own `PartyPaymentHandlers.recordInside` / `cancelInside`, so finance's checks (Parties flag on the place, the account and mode, Back-dated Entry, duplicate reference) are the ones that apply, inside the advance's transaction. Records are made on an issued or closed Work Order (409 `ADVANCE_WORK_ORDER_NOT_ISSUED`); the client side needs the Project's Client (400 `PROJECT_CLIENT_REQUIRED`).
- **One writer per Project.** Every command takes the BOQ lock bills take, so recoveries, releases and a bill's approval or reversal read committed figures.
- **Advance.** Kind (mobilisation or secured), amount (more than ₹0 up to ₹100 crore, one finance payment), date (not after today), recovery mode and value: a % of each bill's gross (two places, more than 0 up to 100; a mobilisation advance on a Work Order left blank takes the Work Order's `mobilisation_recovery_percent`) or a fixed amount per bill (more than ₹0, at most the advance), remarks ≤ 500. The form also takes the account, mode, cheque number or reference and their date, like a party payment. **Migration `20261023090000_construction_contracts_retention_release_invoice`** adds checks (amounts > 0; a given advance names its Work Order, a received one its Client) and an index on `advances.payment_id`.
- **The advance's payment.** Given: an on-account **Payment Out** to the Work Order's Contractor on the Project; received: an on-account **Payment In** from the Project's Client. No allocation, so finance already counts it as an advance on the party (`settledAmount − Σ allocations`, `PartyStore.advances`). Its remarks say "Mobilisation advance on Work Order WO/…". `advances.payment_id` keeps it. It carries no TDS: when finance would suggest 194C TDS on it, the payment records the override reason "An advance recorded in Contracts: no TDS on the advance." (TDS is suggested on the bills' cash payments; see Not yet). Finance shows the payment's `contractAdvance` label and refuses to cancel it or Apply advance from it (409 `PAYMENT_FROM_ADVANCE`, `actions.cancel` / `applyAdvance` false): Contracts applies it through recoveries and cancels it by deleting the advance.
- **Mobilisation advance agreed.** The Work Order's `mobilisation_advance` is the agreed figure. Mobilisation advances given beyond it are a **warning** (`ADVANCES_OVER_AGREED`, shown on the panel), never a refusal. Secured advances do not count towards it.
- **Edit and delete.** An update changes the recovery mode and value and the remarks (409 `ADVANCE_CHANGED` when stale), and the kind only while no live bill (not rejected or reversed) recovers the advance (409 `ADVANCE_RECOVERED`). The amount, date and payment are fixed: delete and record again. Delete is refused while a live bill names the advance (409 `ADVANCE_RECOVERED`, `details.count`) or a guarantee secures it (409 `ADVANCE_HAS_GUARANTEE`); it cancels the payment in the same transaction (its party and account entries reversed).
- **Recovery on bills.** Each bill's view carries `advances`: its contract's advances (the Work Order's given ones, the Project's received ones) with `recovered` (Σ recovery deductions naming it on **approved** bills other than this one), `balance` and `suggested` = min(the rule on this gross, the balance), the rule rounded half up. `GET …/suggestions` answers them as `recoveries`, and `mobilisationRecovery` is now Σ the suggested mobilisation recoveries (null when none). A **new draft** holds the suggested recoveries beside the suggested retention, oldest advance first. On a refresh, a recovery left at its old suggestion follows the new gross (dropped at ₹0); a typed one stays. `secured_advance_recovery` is now accepted on both sides.
- **Every recovery names its advance.** `bill_deductions.advance_id` must be an advance of the bill's contract (400 `BILL_RECOVERY_ADVANCE_REQUIRED` / `BILL_RECOVERY_ADVANCE_INVALID`), the deduction kind must match the advance's (400 `BILL_RECOVERY_KIND_MISMATCH`), once per bill (400 `BILL_RECOVERY_DUPLICATE`), and never above what is left (400 `BILL_RECOVERY_OVER_BALANCE`, `details.max`), with `details.field` `deductions.N.advanceId|amount|kind`. A manual mobilisation recovery without an advance, allowed in CM-1106/1107, is refused now. Approval checks them again under the lock.
- **Accounting: a recovery is the advance applied to the bill.** The bill's `net` is unchanged (gross + GST payable − retention − recoveries). Its finance invoice is **net + the recoveries of advances with a payment**, and approval then allocates that much of each advance's payment to the invoice (`RaBillInvoices.applyRecoveries`: lock the payment, check it is the same party, Project and direction and has that much on account, else 409 `ADVANCE_ON_ACCOUNT_SHORT`; insert the allocation; audited `party_payment.advance_recovered`). The invoice's balance is the net, and the party's balance shows the advance used up. Reversing the bill asks `isSettled` with the bill's own recoveries left out (`ownRecoveries`: allocations from those payments up to those amounts), then takes the allocations back (`undoRecoveries`, `party_payment.advance_recovery_reversed`) before reversing the invoice. The HTTP tests prove the worked example on both sides: advance ₹1,00,000; bill gross ₹4,00,000, 18 % GST ₹72,000, 5 % retention ₹20,000, 10 % recovery ₹40,000 → net ₹4,12,000, invoice ₹4,52,000 settled ₹40,000 by the advance. **Contractor** balance (+ = owed to the Contractor): −₹1,00,000 after the advance; +₹3,52,000 after approval (entries `payment` −1,00,000 and `invoice` +4,52,000); −₹60,000 after a cash payment of ₹4,12,000; reverse refused (409 `BILL_SETTLED`) until that payment is cancelled (+₹3,52,000), then −₹1,00,000 after the reversal, the advance's payment unallocated again. **Client** balance: +₹1,00,000 after the receipt; −₹3,52,000 after approval (`receipt` +1,00,000, `sales_invoice` −4,52,000); +₹60,000 after a ₹4,12,000 receipt; −₹3,52,000 after cancelling it; +₹1,00,000 after the reversal.
- **Retention position.** Per contract: `deducted` = Σ retention on approved running bills (the Work Order's, or the Project's client side); `released` = Σ live releases; **releasable** = deducted − released, which is retention held (Work Order) or receivable (client contract). The completion suggestion is round(completion % × deducted) − released, within what is releasable; the DLP-end suggestion is everything releasable. The bill cap (CM-1106) still counts what was deducted, not what is held: releases do not make room under it.
- **Retention release.** Stage completion, DLP end, against a bank guarantee, or other; an amount of more than ₹0 up to what is releasable (400 `RELEASE_OVER_RELEASABLE`, `details.max`); a date not after today; a reason (≤ 500) required for other. **Completion** and **DLP end** need the DLP start (409 `COMPLETION_DATE_REQUIRED`) and a release on or after it. **DLP end before the DLP ends** (decided here): 409 `DLP_NOT_ENDED` (`details.dlpEndsOn`) unless the caller holds the side's **Approve**, and then a reason is required (400 `RELEASE_REASON_REQUIRED`); the audit marks it `beforeDlpEnd`. **Against a bank guarantee**: it names one (400 `RELEASE_GUARANTEE_REQUIRED`) of purpose retention on the same contract, unreleased and unexpired on the release date (400 `RELEASE_GUARANTEE_INVALID`); the amount is any part of what is releasable.
- **The release's invoice.** Finance gains origin **`retention_release`** (migration `20261023090100_construction_finance_retention_release_origin`, `construction_finance` only, widening `invoices_figures_check`: a contracts origin with a source, payable to a Contractor or receivable from a Client, and a release's invoice has no taxable value or GST). Created in the release's transaction through `PartyInvoicing.createRelease` → `RaBillInvoices.createRelease`: the Contractor's payable on the Project with the Work Order's Department, or the Client's receivable; dated the release; no due date; amount = the release; `source_id` = the release; remarks "Retention released on Work Order WO/… (on completion)". Its number is `WO/…/RET-n` (the Work Order's number) or `RET-n` (client contract), n counting the contract's releases deleted ones included, and "-2", "-3"… when the party already has a live invoice with it. Its one party entry is `invoice` +amount or `sales_invoice` −amount, so the party's balance moves from held to due. `retention_releases.invoice_id` keeps it and `client_id` the Client (client side), both added by the contracts migration with a check (a contractor release names its Work Order, a client one its Client). It is read-only in finance (409 `INVOICE_FROM_RETENTION_RELEASE`, "This invoice comes from a retention release on WO/…. Delete the release in Contracts to change it."; `actions.edit`/`delete` false); the invoice response carries `retentionRelease` (side, Work Order id and number) read through `FinanceDirectory.retentionReleases`.
- **Delete a release.** Delete, with a reason (400 `DELETE_REASON_REQUIRED`, ≤ 500, kept in the audit `retention_release.deleted`), while nothing is paid, received, written off or pending write-off against its invoice (409 `RELEASE_SETTLED`). The invoice's entry is reversed and the invoice tombstoned (`invoice.removed_with_retention_release`); the retention is held (receivable) again.
- **Retention held and receivable now subtract releases** everywhere they show: the Contractor Bills list (per Contractor, through `AdvanceStore.releasedByContractor`), each Contractor Bill (`retentionHeldOnWorkOrder`), the Client Bills list, each Client Bill and the client contract terms (`retentionReceivable`), and finance's Client balance (`clientRetentionReceivable` subtracts the client-side releases by `client_id`).
- **Bank guarantees.** Purpose advance (naming an advance of the same contract: 400 `GUARANTEE_ADVANCE_REQUIRED` / `GUARANTEE_ADVANCE_INVALID`), retention or performance; number ≤ 60, bank ≤ 120, amount more than ₹0, issued on (not after today), expires on or after it. On a Work Order (contractor) or the client contract (client). Editable until released (409 `GUARANTEE_RELEASED`; 409 `GUARANTEE_CHANGED` when stale); a retention guarantee something was released against keeps its purpose and cannot be deleted (409 `GUARANTEE_IN_USE`). **Mark released** records the date it went back to the bank (on or after issue, not after today). Status: live, expired (past expiry), released; the panel shows "Expires in N days" within 30 days.
- **DLP.** Contractor side: starts on the Work Order's `completed_on` — set when it closes or its Final bill is approved (CM-1104/1106), or recorded with `POST …/work-orders/{id}/completion` (Work Order Update; an issued or closed Work Order, 409 `WORK_ORDER_STATUS_INVALID` otherwise; on or after the order date, not after today; audited `work_order.completion_recorded`). Client side: starts on `client_contracts.handover_on` (the terms dialog). End = start + DLP months in calendar months (31 Jan + 1 → 28/29 Feb), the start itself without DLP months. The panel shows start, months, end and days left.
- **Daily notice `contracts.deadlines_due`.** Queue job `messaging.contract_deadlines` in `DAILY_JOB_TYPES`, like `inquiry.follow_ups_due`: the composition source reads live unreleased guarantees expiring and DLP ends (Work Orders issued or closed with a completion date; client contracts with a handover date) within 30 days of each Company's today, per Project. One notification per member per Project a day (source key `contracts.deadlines_due:{projectId}:{date}`), listing what the member may see: a Work Order's to Work Order Read + Notification holders, the client contract's to Client Bills Read + Notification holders. Title "1 bank guarantee expires and 1 DLP ends within 30 days in {Project}", body one clause per item; it links the Work Order (one), the Work Orders list (several or mixed) or the Client Bills page (client only), and carries the Client Bills menu when it holds only client items.
- **Audit.** `advance.recorded|updated|deleted`, `bank_guarantee.added|updated|released|deleted`, `retention.released`, `retention_release.deleted` (with the reason), `work_order.completion_recorded`, and finance's `party_payment.recorded|cancelled|advance_recovered|advance_recovery_reversed`, `invoice.created_from_retention_release|removed_with_retention_release`.
- **Not yet.** TDS on a given advance: the advance's payment records none, and the bills' cash payments suggest TDS on the cash only, so the recovered part is not in any TDS base; CM-1116 should decide whether the advance or its recovery carries 194C. No Back-dated Entry module for advances, guarantees and releases (the advance's payment does check `party_payment`'s). The bill PDFs print the recovery's kind, not the advance's date. Backups (CM-907) do not include the contracts tables yet.

### CM-1109 — Price indices and escalation bills

- **Where it is.** Master records → Contracts → **Price indices** (`/app/masters/price-indices`), beside the Item Library: one card per series with its months, Add index / Add month, edit and delete per month, Import (with the rows at fault) and Export. **Permission: the Item Library's menu `contracts.items`** (Read lists, Create adds, Update edits a value, Delete removes, Import and Export move the sheet): price indices are the same kind of Company-level contracts master and the matrix needs no new row. No sparkline: `@repo/ui` has none and no chart library was added. The **escalation clause** is a panel on the Work Order page (contractor side) and on the Client Bills page below the client contract terms (client side). Escalation bills have their own page, `/app/projects/{id}/contractor-bills/escalation/{billId}` (or `client-bills/escalation/…`); the bill lists show them with their type and period and link there, and both lists offer **New escalation bill**.
- **Price indices.** Series names are free text (≤ 80, spaces collapsed) with suggestions (WPI – All commodities, CPI-IW, WPI – Cement, WPI – Steel, WPI – Bitumen, WPI – HSD (POL)), matched to a series already kept **ignoring case**, which keeps its first spelling. A month is `YYYY-MM` (stored as its first day, checked by `price_indices_figures_check`); a value is more than 0 with four places (`DECIMAL(12,4)`). One per series and month (409 `PRICE_INDEX_EXISTS`); the value can be edited (409 `PRICE_INDEX_CHANGED` when stale), the series and month cannot (delete and add). Deleting a month is allowed at any time: approved escalation bills keep the working they were approved with, and a draft needing the month is refused when next worked out. Audited `price_index.created|updated|deleted`.
- **Import and export.** One sheet (`Price indices`), columns Series, Month and Value found by header. A month cell may be an Excel date (any day of the month), `2026-04`, `2026-04-01` or `Apr 2026`. A new series and month is added, an existing one has its value replaced, the same value counts as `unchanged`. All or nothing: 400 `IMPORT_HAS_ERRORS` with `details.errors` = [{ row, column, message }] (a series and month twice in the sheet is an error naming the first row), `IMPORT_EMPTY`, `IMPORT_TOO_MANY` (2,000 rows), 5 MB, `.xlsx` only. The export writes every index in the same columns, so it imports back. Imports write one audit event per changed month (`source: "import"`) in one insert (`recordAudits`).
- **The clause.** One per Work Order and one per client contract (the CM-1101 partial indexes; 409 `ESCALATION_CLAUSE_EXISTS`). Base month `YYYY-MM`, not after this month; non-escalable % from 0 to below 100, blank 15; one row per component (labour, material, cement, steel, bitumen, POL, other; 400 `ESCALATION_COMPONENT_DUPLICATE`), each with an index series and either a **weight** (`weighted`, 10CC: more than 0 up to 100, two places) or, for **cement and steel only**, a **base price** (`quantity`, 10CA, paise a unit; 400 `ESCALATION_BASIS_INVALID`, `ESCALATION_BASE_PRICE_INVALID`). The weighted components' weights add up to exactly 100 (400 `ESCALATION_WEIGHTS_NOT_100`, `details.total`). **Migration `20261023120000_construction_contracts_escalation`** (`construction_contracts` only) adds `escalation_clause_components.basis` (enum `escalation_basis`, default `weighted`) and `base_price`, `bill_deductions.escalation_bill_id`, and checks on components (weighted: weight > 0, no base price; quantity: weight 0, base price > 0), clauses (NE 0–<100, side matches `work_order_id`), indices and escalation bills (period and working present). Deployed to `construction_m11` and `construction_test_m11`.
- **Clause permission.** Read on `contracts.work_orders` (contractor) or `contracts.client_bills` (client) sees it; weights, NE % and base prices are null without that menu's **Financial**. Adding, editing and removing need **Update and Financial** (403 without Financial: the clause is money terms). The client side needs a Contract work Project (400 `PROJECT_NOT_CONTRACT_WORK`). **Locked once used:** while any approved escalation bill on the contract exists, edit and remove are 409 `ESCALATION_CLAUSE_USED` (`details.count`). A clause can only be removed while unused, so every approved bill on a contract used its live clause; the bill's working also stores the clause id. Audited `escalation_clause.created|updated|deleted`.
- **HTTP shape.** Like CM-1108: reads where the panels are (`GET …/work-orders/{id}/escalation-clause`, `GET …/client-bills/contract/escalation-clause?projectId=`), writes in a sibling area whose body names the contract (`POST …/escalation-clauses` with `projectId` and `workOrderId` or none, `…/escalation-clauses/{id}/update|delete`). Price indices under `…/contracts/price-indices/**`. **Escalation bills are a separate area, `…/contracts/escalation-bills/**`** (create with `projectId` and `workOrderId` or none, `form-options?projectId&side`, `preview`, `/{id}`, `/{id}/update|refresh|delete|submit|approve|reject|reverse`, `/{id}/pdf`), not a `type` on the RA routes: the RA handlers are built around measurement rows, lines and Final bills an escalation bill has none of, so a separate handler on the shared engine (`ra-bill.ts` header, GST, deductions, net, life; `ra-bill-common.ts` stale check, approval, events, deduction plan, snapshot; `prisma-ra-bill-rows.ts` columns, deductions, tombstone) is smaller and keeps both sides in one place. The RA lists (`GET …/contractor-bills`, `…/client-bills`) answer both types with `type`, `periodFrom` and `periodTo` and take a `type` filter; `GET …/contractor-bills/{id}` stays RA only (404 for an escalation bill). Access: the bill's side menu (Contractor Bills or Client Bills), 403 before 404; another Company's bill is 404 `BILL_NOT_FOUND`.
- **Period: whole months only.** Indices are monthly, so a period is `fromMonth`–`toMonth` (no part months): after the clause's base month (400 `ESCALATION_PERIOD_BEFORE_BASE`), at most 12 months (400 `ESCALATION_PERIOD_TOO_LONG`), ending on or before the bill date (400 `ESCALATION_PERIOD_AFTER_BILL_DATE`). The bill date follows the RA rules (not after today; on the contractor side not before the Work Order's date) and the side's Back-dated Entry module (`contractor_bill` / `client_bill`).
- **R and its bills.** R = Σ gross of the side's **approved** running bills on the contract (the Work Order; on the client side the Project) whose **bill date** falls in the period; drafts, pending, rejected and reversed ones are left out. None is 400 `ESCALATION_NO_BILLS`. The working records each bill's id, number, date and gross. A running bill an escalation bill (live, not rejected or reversed) takes cannot be reversed: 409 `BILL_IN_ESCALATION` on both RA sides (reverse or delete the escalation bill first). A running bill approved later with a date in an already approved escalation period is not escalated; draft escalation bills after the period's RA bills are approved.
- **The working** (`domain/escalation.ts`). Per weighted component: amount = R′ × (1 − NE/100) × weight/100 × (Ī − I₀)/I₀, with I₀ the series in the base month and Ī the average of the period's monthly values, kept as an exact fraction (Σ − n·I₀)/(n·I₀); each amount is rounded **once, half away from zero, to the paisa** (as the Measurement Book rounds deductions). Ī (four places) and the factor (six places) are shown rounded for reading only. Gross = Σ amounts. A missing index (the base month first, then each month in order) is 400 `PRICE_INDEX_MISSING` with `details.series` and `details.month`. Series are matched to indices ignoring case.
- **10CA for cement and steel.** A `quantity` component's amount is quantity × base price × (Ī − I₀)/I₀, with no non-escalable share. Its value at the base price (Σ quantity × base price) is **taken out of R before the 10CC part** (R′ = max(0, R − that), shown as "R for 10CC"), because CPWD escalates materials covered by 10CA only through 10CA; escalating them again through the material weight would count them twice. The quantity used in the period comes from **material reconciliation** when the component names a Material (CM-1110, below), else it is typed on the draft (`quantities` on create and update, 0 or more, four places; a blank one is 0 and the page warns `ESCALATION_QUANTITY_MISSING`). `EscalationDeps.materialQuantities(db, { workspaceId, contract, period })` (wired in `src/composition/contracts-escalation.ts`) is asked first and typed quantities override it; a draft keeps the quantities it was created with, so they stay editable and submit and approve compare the same working.
- **Worked figures the tests assert.** R ₹10,00,000 (₹4,00,000 on 30 Apr and ₹6,00,000 on 15 Jun 2026; a March bill, a reversed and a draft May bill and another Work Order's bill left out), NE 15 %, base Jan 2026, period Apr–Jun 2026: labour 30 % CPI-IW 140 → 147 = ₹12,750; material 50 % WPI 150 → avg(153, 156, 159) = 156 = ₹17,000; POL 20 % 120 → avg(113, 114, 115) = 114 = −₹8,500; **gross ₹21,250**; GST 18 % ₹3,825 (CGST ₹1,912.50 + SGST ₹1,912.50); retention 5 % ₹1,062.50; **net ₹24,012.50**, the payable invoice ₹24,012.50 (taxable ₹21,250, GST ₹3,825). Negative: POL 100 % → −₹42,500. 10CA (unit test): 120 units of cement at ₹7,000, WPI cement 100 → 110: ₹84,000; R′ = ₹1,60,000; labour 100 % at +5 %: ₹6,800; gross ₹90,800. Client side: labour 100 % on R ₹10,00,000 → ₹42,500, GST ₹7,650, retention ₹2,125, net and receivable ₹48,025.
- **GST and deductions.** GST on the escalation gross at the side's RA terms: the Work Order's SAC, rate and reverse charge with the Contractor's state against the Project's (contractor side); the client contract's rate as a tax invoice with the Company GSTIN for the Project's state and the Client's GSTIN, `GSTIN_NOT_IN_STATE` as a warning (client side). Deductions are **retention** and **other** only (400 `BILL_DEDUCTION_KIND_INVALID` for advance recoveries: those are suggested on running bills, never here). Retention is suggested at the side's % on the gross, cut to the cap, and **the cap counts both types**: retention held for the cap (the Work Order's or the Project's client side) now sums retention on approved bills of either type, and so do retention held, retention receivable, the releasable figure (CM-1108) and finance's Client retention receivable — the `type = 'running'` filters on those four sums were removed. A new draft holds the suggested retention; on a re-working, retention left at the old suggestion follows the new gross (the RA deduction plan). All deductions are at most gross + GST payable.
- **Numbers and life.** Escalation bills take the side's sequence (`contractor_bill` / `client_bill`) at first submit, dated the bill date, and an **ordinal of their own** (the CM-1101 ordinal indexes include `type`): "Escalation 1, 2, …" on the contract. A draft is changed, worked out again (**Refresh**: bills approved and indices typed since), deleted or submitted by its creator with Create or an Update / Delete holder; Approve and Reject use the approval kernel and raise `document.*` with the new approval types **`contractor_escalation_bill`** and **`client_escalation_bill`** (`APPROVAL_DOCUMENTS`, the side's menu, linking to the escalation page). **Several drafts per contract are allowed** and may overlap one another; **one per period is enforced against approved and pending ones**: a draft, a period change, submit and approve are refused with 409 `ESCALATION_PERIOD_OVERLAP` (`details.number`, `periodFrom`, `periodTo`) when another escalation bill on the contract that is pending or approved overlaps it.
- **Nothing moves under a bill.** Submit and approve work the bill out again from what it stored (period, quantities) and compare the bills taken, indices, clause and amounts (`workingSignature`); any change is 409 `ESCALATION_WORKING_CHANGED` (refresh a draft; reject a pending bill and draft again). A gross of exactly ₹0 cannot be submitted (409 `ESCALATION_GROSS_ZERO`).
- **Approval and finance.** As RA bills: a positive net creates the finance invoice through `PartyInvoicing` (origin `ra_bill`, the bill as `source_id`, number and date the bill's, taxable = gross, GST = GST payable, amount = net): payable to the Work Order's Contractor with its Department, or receivable from the Project's Client. It is read-only in finance like an RA bill's; finance's invoice response gains **`raBillType`** (`running` | `escalation`, read through `FinanceDirectory.raBillTypes`) so the invoice sheet says "From Escalation Bill …" and links to the escalation page. **Reverse** (Approve) only the latest approved escalation bill on its contract (409 `BILL_NOT_LATEST` while one with a higher ordinal is approved; RA bills do not block it and it does not block them), with nothing paid against its invoice (409 `BILL_SETTLED`); finance reverses the entry and tombstones the invoice. Audited `escalation_bill.created|updated|deleted|submitted|approved|rejected|reversed` (snapshots add side, period, R and the bills taken).
- **Negative escalation: recovered on the next running bills.** CPWD 10CC works both ways. A bill whose indices fell has a negative gross, no GST and no deductions; it is approved **without an invoice** (a negative invoice would be a credit note, CM-1113's work). Its size is then **recovered on the contract's next running bills** as an **`other`** deduction naming it (`bill_deductions.escalation_bill_id`, reason "Escalation recovery on CB/… (Apr 2026 – Jun 2026)"): a new RA draft holds the suggestion after retention and advance recoveries, cut to what the bill can take (gross + GST payable − the rest), oldest period first; the rest stays for later bills. Each RA bill answers `escalationRecoveries` (number, period, amount, recovered on other approved bills, balance) and the editors offer "Use". Such a deduction must name an approved negative escalation bill of the same contract (400 `BILL_ESCALATION_RECOVERY_INVALID`), once per bill (`…_DUPLICATE`) and not above what is left (`…_OVER_BALANCE`, `details.max`), checked again at approval. The recovery is a plain deduction: it lowers the RA bill's net and invoice, not its taxable value (the GST adjustment by credit note is CM-1113's). A negative bill that a live running bill recovers cannot be reversed (409 `ESCALATION_RECOVERED`).
- **PDF.** `GET …/escalation-bills/{id}/pdf` (Print) titled **"Escalation Bill"**: the letterhead, Project, period, the party and Work Order or client contract, base month and NE %, the running bills in R with their gross, the **working** (component, weight or quantity × base price, series, I₀, each month, Ī, factor, amount), the formula, GST, deductions and net (and the recovery note when negative), signatures. Indices only without Financial.
- **Screens.** The New escalation bill dialog picks the Work Order (only those with a clause) or the client contract, the months and the bill date, and shows R with the bills it takes and the escalation before drafting (or the refusal, e.g. the missing index). The escalation bill page shows status and actions by `allowed`, the working as cards at 375 px and a table from md up, the bills in R, GST, deductions, net, the recovery position, and the draft's editor (period, bill date, 10CA quantities, retention and other deductions, remarks). The clause panel shows the components and the lock, and its dialog keeps a running weight total.
- **Not yet.** Backups (CM-907) do not include the price indices, clauses or escalation bills. The GST adjustment of a negative escalation (credit note) and e-invoice JSON are CM-1113. No sparkline on the indices page.

### CM-1110 — Material reconciliation

- **Where it is.** A **Material reconciliation** panel on an issued or closed Work Order that issues materials (`/app/projects/{id}/work-orders/{workOrderId}#reconciliation`, `?billId=` opens it at a bill): a bill picker (the latest approved bill by default, else the open one, else "to date"), per material theoretical, allowed, issued, excess, an under-use flag, the penal rate and the recovery (recovered on an approved bill, suggested on a draft or pending one), a table from md up and cards at 375 px; the unattributed issues with **Assign to this Work Order**; and **Statement PDF**. A Contractor Bill links to it ("Material reconciliation"), and its deductions editor offers **Material recoveries** beside the advance and escalation recoveries.
- **HTTP shape.** `GET …/work-orders/{id}/reconciliation?billId=` (Work Order **Read**; money null without its **Financial**; 404 `BILL_NOT_FOUND` for a bill that is not a live, not rejected or reversed running bill of the Work Order; another Company's Work Order 404 `WORK_ORDER_NOT_FOUND`) and `…/reconciliation/pdf?billId=` (**Print**). The statement answers `canAssign` (Material Requests **Update** with the Team Member on the Project). Quantities are strings with three places in the material's UoM; money is paise.
- **What was issued.** An **issue** is a line of a **delivered** Delivery Note (`delivered_on` set) of a live Material Request raised for the Contractor on the Project, dated its "delivered on": the material reached the site for that Contractor. An approved note still in transit is not issued yet. Contracts reads them through the `MaterialIssues` port (`application/reconciliation-ports.ts`); `src/composition/contracts-material-issues.ts` adapts procurement's tables, so neither context imports the other.
- **Attribution rule** (`attributeIssue`, `domain/material-reconciliation.ts`):
  1. A Material Request may name a **Work Order** (migration `20261023150000_construction_procurement_material_request_work_order`, `construction_procurement` only: `material_requests.work_order_id`); its Delivery Notes count towards that Work Order. The MR form offers the picked Contractor's **issued** Work Orders on the Project (400 `WORK_ORDER_NOT_FOUND`, `WORK_ORDER_NOT_FOR_CONTRACTOR`, `WORK_ORDER_NOT_ISSUED`, `MATERIAL_REQUEST_CONTRACTOR_REQUIRED`, all on `workOrderId`); one it already names may stay after the Work Order closes.
  2. Otherwise an issue counts towards the Contractor's Work Order on the Project that lists the material and was **open on the issue's date** (ordered on or before it; issued, or closed on or after it) when there is exactly one. Taking only Work Orders open on the date keeps a later Work Order from taking earlier issues away, so a statement does not change when a second Work Order is issued.
  3. With none or several it is **unattributed**: shown on each Work Order of the Contractor that lists the material, counted nowhere. **Assign** is procurement's command, `POST …/procurement/material-requests/{id}/assign-work-order` (Material Requests **Update**, on the Project; an issued or closed Work Order of the request's Contractor; 409 `MATERIAL_REQUEST_WORK_ORDER_SET` when it already names one; audit `material_request.work_order_assigned`). It works after Delivery Notes, which lock the request's own edit. A request names one Work Order, so all its notes move together.
- **Returns.** Procurement has **no return flow** (stock movements are consumed, missing and adjustment; transfers move between stores and sites). `MaterialIssues.returnsFrom` answers none and the statement says `returnsRecorded: false` ("Returns from the Contractor are not recorded yet"); a return flow plugs in there and is attributed like an issue.
- **The statement** (per Work Order per running bill B, cumulative, per material, keyed on (Work Order, Material) — never the `work_order_materials` row id, which saving replaces):
  - **billed** per line = the line quantities of the Work Order's **approved** running bills before B (a lower ordinal; all approved ones when B is a draft) plus B's own lines whatever its status;
  - **theoretical** = Σ billed × the line's coefficient; **allowed** = theoretical × (1 + wastage %); **under-use limit** = theoretical × (1 − wastage %);
  - **issued** = issues counted towards the Work Order delivered on or before B's **"measured up to"** (not its bill date: material for work not yet measured is not held against the bill), less returns;
  - **excess** = max(0, issued − allowed); **under-use** when issued < the limit;
  - exact arithmetic in 10⁻¹² of the UoM (quantities are ten-thousandths, issues thousandths), shown to three places half up and priced half up to the paisa.
- **Worked figures the tests assert.** PCC 175 cum, cement 6.34 bag/cum, 2 % wastage, ₹500 a bag. Bill 1: 100 cum, 700 bags → theoretical 634.000, allowed 646.680, excess 53.320, ₹26,660. Bill 2: 120 cum cumulative, 790 bags → 760.800, 776.016, excess 13.984, ₹6,992 cumulative, already ₹26,660 recovered → **₹0 more** (never a refund). Under-use: 600 bags against 634 (limit 621.320) is flagged. Steel at cost at ₹60 a kg: 100 kg → ₹6,000 on bill 1, 50 kg more → ₹3,000 on bill 2.
- **Recoveries on the bill.** `bill_deductions.material_id` (migration `20261023150100_construction_contracts_material_reconciliation`, `construction_contracts` only; a check keeps it on the two material kinds and requires it on a reconciliation recovery). The draft being prepared is "the next bill": its own statement suggests
  - **material reconciliation recovery**, one line per material, = max(0, cumulative excess × penal rate − Σ such recoveries on earlier approved bills); none without a penal rate;
  - **material issued at cost** = max(0, at-cost issues × issue rate − Σ at-cost deductions naming the material on earlier approved bills) — the same as "issues since the previous approved bill, unless already deducted", without date gaps. Manual at-cost lines without a material still work and are not counted.
  - **Capped to what the bill can take.** All deductions are at most gross + GST payable (`BILL_DEDUCTIONS_TOO_LARGE`), so what is **due** (above) is only **offered up to what fits**: min(due, gross + GST payable − the bill's other deductions). The rest stays due: earlier approved recoveries are subtracted from the cumulative figure, so it is suggested again on the next bills. The bill detail and `…/suggestions` answer `recoveryFits` and `atCostFits` beside the due figures, and the editor shows "₹6,992.00 due · ₹2,412.00 fits this bill" and fills "Use" with what fits of the deductions as typed. A typed amount above it is still refused with `BILL_DEDUCTIONS_TOO_LARGE`.
  - **Priority when suggestions compete** for the room on a new draft (and on a refresh): **retention** (the Work Order's %, within its cap) → **advance recoveries** (oldest advance first) → **material reconciliation recoveries** (Work Order material order) → **material issued at cost** → **escalation recoveries** (oldest period first). Retention and advance recoveries are contract terms on every bill; the material penal recovery is the Company's own claim on this bill's work; at-cost material is a sale that can wait a bill; a negative escalation recovery is the slowest to go stale and keeps following later bills. On a refresh, material lines without a reason are trimmed last-first when the bill has shrunk, so the draft still saves. On a refresh or an edit that keeps the deductions, a material line left at its old suggestion follows the new one (CM-1108's rule, keyed by kind and Material), and a material newly suggested where nothing was before is added.
  - **Limits.** A reconciliation recovery names a Material the Work Order issues (400 `BILL_MATERIAL_REQUIRED`, `BILL_MATERIAL_INVALID`), at-cost names an at-cost one, once per kind and material (400 `BILL_MATERIAL_DUPLICATE`). It may be edited **down** freely; **above** the suggestion it needs a reason in its description (400 `BILL_MATERIAL_RECOVERY_REASON_REQUIRED`, `details.max`) **and** Contractor Bills **Approve** (403 `BILL_MATERIAL_RECOVERY_OVER_SUGGESTION`). A line sent back unchanged is not checked again; on a refresh a reasonless line now above its suggestion is cut to it (dropped at ₹0), like retention above its cap.
  - **Client bills** issue no material: a reconciliation recovery is refused by kind (the request model's enum, 400 `VALIDATION_ERROR`) and no client deduction names a Material.
  - The bill detail and `…/suggestions` answer `materials` (excess, penal rate, recovered before, suggested, at cost); the PDF prints a material deduction as "Material reconciliation recovery (Cement OPC 53)".
- **10CA quantities.** A quantity (10CA) clause component on a Work Order may name a **Material** it issues (`escalation_clause_components.material_id`, quantity basis only; 400 `ESCALATION_MATERIAL_INVALID`, the client side names none). `materialQuantities` answers, per such component, Σ over the Work Order's **approved running bills dated in the period** of each line's quantity × coefficient, half up to ten-thousandths (100 cum × 6.34 → 634.0000 bags). The clause editor offers the Work Order's materials ("Quantity from", or "Typed on the bill"); the base price must then be per the material's UoM.
- **PDF.** "Material Reconciliation" on the shared page writer: the letterhead, Project, Contractor, Work Order, bill and "issues up to", the statement table, material at cost, the issues counted and the returns note, signature blocks. Plain glyphs only (CM-1109 printed "I₀" as a box): no subscripts or superscripts. Quantities only without Financial.
- **Not yet.** A return flow in procurement; per-issue (rather than per-request) assignment; backups (CM-907) of reconciliation data beyond what bills and requests already hold.
