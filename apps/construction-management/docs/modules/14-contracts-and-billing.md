# 14 — Contracts & Billing

The build spec for **M11 part 1** (CM-1101 … CM-1111): the Company's Item Library, a Project's BOQ and Variations, Work Orders, the Measurement Book, client and contractor RA bills, advances, retention, escalation and material reconciliation. It lives in the `contracts` context (`src/contracts`, Postgres schema `construction_contracts`, API prefix `/api/construction/contracts`).

The product decisions are in [ADR CM-0023](../adr/CM-0023-india-compliance-product-decisions.md) (§1–§10, §22). This page does not repeat them. It records the smaller decisions each ticket had to make while building, which the ADR left open. Each ticket appends its own list below.

## Decisions for the build (M11)

### CM-1102 — Item Library

- **Where it sits.** Master records gains a **Contracts** group holding **Item Library** (`/app/masters/item-library`). It matches the Contracts sidebar heading and the Contracts & Billing permission category. Later contracts masters (price indices for escalation, §9) can join it. Placing it beside Materials would mix what you buy with what you bill.
- **List order.** Items are listed in **code order**, not newest first, because a schedule is looked up by its code. The cursor carries the code and id. The total counts the filter.
- **Search and filter.** The search matches part of the code, the short description or the long description, ignoring case. The schedule filter is an exact match on one schedule label from the distinct live labels (`GET …/items/schedules`).
- **Limits.** Code ≤ 32 characters, short description ≤ 200, long description ≤ 4,000 (it keeps its line breaks), schedule ≤ 80, at most 100 analysis lines, a line description ≤ 200. SAC/HSN is 4–8 digits.
- **Money and numbers.** Rates, line amounts and the analysed rate are integer paise from ₹0 to **₹1,000 crore** (10¹³ paise). That keeps every figure exact as a JSON number, the way other contexts send `BIGINT` money. Sums run in `bigint`. A coefficient is more than 0 and at most 10,00,000, with four places, and is sent as a string (`"0.4500"`). The overhead and profit is 0–100 % with two places (`"15.00"`).
- **Rounding.** A line's amount is `round(coefficient × rate)`. The analysed rate is `round(Σ amounts × (1 + overhead / 100))`, rounded once over the sum. Both round half up. The form works it out the same way while you type.
- **Lines by kind.** A line keeps only the reference its kind needs; any other reference sent is dropped. A **lump sum** has coefficient 1, no resource UoM, and a required description. Its rate is per Item unit. A **material line** without a resource UoM takes the Material's UoM.
- **Picked masters.** A Material, Labour Category, Equipment or UoM must belong to the Company and be live and enabled. One the Item already has may stay after it is disabled or removed, so an old Item can still be saved. The same applies to the Item's own UoM. The errors are 400 `ITEM_UOM_INVALID` and `ANALYSIS_{MATERIAL,LABOUR_CATEGORY,EQUIPMENT,UOM}_INVALID`, with `details.line` (from 0) and `details.field` (`lines.N.materialId`).
- **Overhead without lines.** The overhead is stored as typed even with no lines. The analysed rate is null without lines.
- **Rate suggestions.** Picking a Material on a material line fills a blank rate with the Material's unit rate. This happens only when the caller holds the **Materials** menu's Financial flag; otherwise the picker sends no rate. Labour Categories have no wage in Master records, so labour lines get no suggestion. CM-1118's minimum-wage cards can add one later.
- **Pickers.** The form reads its UoMs, Labour Categories and Equipment from `GET …/items/form-options` and Materials from `GET …/items/material-options` (a server search). Both need Item Library create or update, so a Team Member without Materials or Equipment read can still build an analysis. Materials, Labour Categories and Equipment are pickers you can search. UoMs are a plain select.
- **Flags on screen.** The list response carries `viewerFlags`: the Item Library flags the caller holds. The screen hides Add, Edit, Delete, Import, Sample and Export by them. Every route checks again. (`…/contracts/access` needs a Project, and the Item Library is Company-wide.) A Team Member with View only sees the list, and codes are not links.
- **Delete guard.** Delete locks the Item row, then counts live BOQ items (`boq_items.item_id`, `deleted_at IS NULL`) in the same transaction. 409 `ITEM_IN_USE` carries `details.count`. CM-1103 should take the same row lock (or `FOR SHARE`) when it copies an Item into a BOQ.
- **Optimistic checks.** Update needs `expectedUpdatedAt` (409 `ITEM_CHANGED`). Delete checks it when sent. Update replaces every analysis line in the same transaction; the lines get new ids.
- **Import.** The sheet's columns are Code, Short description, Description, UoM, SAC/HSN, Schedule and Rate (₹), found by header, so the order is free. Rows match Items by Code, ignoring case. A new code adds an Item with no analysis. An existing code has its fields replaced, and a blank optional cell clears that field. Its analysis lines, overhead and analysed rate stay. A row identical to its Item counts as `unchanged`. The UoM is matched by **name** ignoring case, because Measurement Units have no symbol column. An existing Item may keep a UoM that has since been disabled. A code twice in one sheet is a row error naming the first row. The rate is rupees with at most two places: a number cell, or text like `6,123.45` or `₹6123.45`. The import is all or nothing: 400 `IMPORT_HAS_ERRORS` with `details.errors = [{ row, column, message }]`, where `column` is the sample's header. Each row reports one problem per column. At most 2,000 rows and 5 MB, `.xlsx` only.
- **Import audit.** An import writes one `item.created` or `item.updated` audit event per changed Item, marked `source: "import"`, in one `createMany`.
- **Sample and export.** The sample has the headers and two example rows (a CPWD DSR item and an "Own" item). Downloading it needs the **Import** flag. The export writes the list's current search and schedule in the sample's columns, in code order, so it can be edited and imported back. It needs the **Export** flag and holds at most 10,000 Items (400 `EXPORT_TOO_MANY`).
- **Not yet.** Backups (CM-907) do not include the Item Library yet. A later contracts ticket adds the contracts tables to the backup modules together.

### CM-1103 — BOQ

- **Where it is.** Project → Contracts → **BOQ** (`/app/projects/{id}/boq`), one page with three tabs: **Items** (the sections), **Variations** and **Deviations**. `?tab=variations` opens the Variations, which is where a Variation's notification links. The total bar above the tabs shows the BOQ total, the Project's Order Value and the difference (total − Order Value).
- **HTTP shape.** Everything is under `/api/construction/contracts/boq`. Collection reads and creates name the Project (`?projectId=`, or `projectId` in the JSON body), and records use their id (`/sections/{id}`, `/items/{id}`, `/variations/{id}`), like the sales module. Access is checked first: 403 `PERMISSION_DENIED` for a Team Member not on the Project, then 404 `PROJECT_NOT_FOUND` for a Project that is not the Company's. A record of another Company is its own 404 (`BOQ_SECTION_NOT_FOUND`, `BOQ_ITEM_NOT_FOUND`, `VARIATION_NOT_FOUND`). Updates are named operations (`…/update`, `…/move`, `…/delete`, `…/approve`, `…/reject`, `settings/update`), like every other module, rather than `PUT`.
- **One read for the whole BOQ.** `GET …/boq?projectId=` answers every live section and item in order, with subtotals, the total, the measured flags and any pending Variation per item. A BOQ is a document read as a whole, so it is not paged. An import is capped at 5,000 rows.
- **One writer per BOQ.** Every BOQ and Variation command first takes a transaction advisory lock on the Project's BOQ (`construction_contracts.boq:{workspace}:{project}`). That settles positions, item numbers, the measured check and "one pending change per item" without new indexes. The partial unique indexes on titles and numbers are still the last word (P2002 → 409).
- **Limits and numbers.** A section title is at most 120 characters. An item no is at most 32, and a description at most 4,000 (line breaks kept). SAC/HSN is 4–8 digits. A quantity is more than 0 with four places, below 10¹², sent as a string (`"12.5000"`). A rate is integer paise from ₹0 to ₹1,000 crore, and a line's amount (`round(quantity × rate)`, half up) is at most ₹1,000 crore (400 `BOQ_AMOUNT_TOO_LARGE`). Subtotals and the total are sums of the rounded lines.
- **Original and current.** A new item's original quantity and rate are the ones given. Before any checked measurement, an edit corrects the contract: the original moves with the current figure while the two are still equal. Once an approved Variation has made them differ, an edit changes only the current figure.
- **Measured.** An item is measured when a row of a live measurement sheet with status `checked` names it (`measurement_rows.boq_item_id`). Measurement rows that name BOQ items are the client side, so the side is not filtered again. Once it is measured, a new quantity or rate (by the form or by import) is refused with 409 `BOQ_ITEM_MEASURED`, and so is a delete. The item no, description, UoM, SAC/HSN, Wing or Location and section stay editable. The measured quantity is the sum of those rows (deductions included). The check runs inside the BOQ lock. CM-1105 should take the same lock (or lock the item rows) when it checks a sheet, so a check and an edit cannot cross.
- **Wing or Location.** An item may name a Wing on a building Project or a Location on one with Locations (by `structure` from the directory), never both (400 `BOQ_ITEM_PLACE_INVALID`). A Wing or Location the item already has may stay after it is removed.
- **Item Library copy.** The form's picker reads `GET …/boq/library-items` (code or description, 25 at a time). It needs BOQ create or update, not Item Library read. The adopted rate is sent only with BOQ Financial. Picking fills the item no (when blank) with the code, the description (the long one, or the short one), the UoM, SAC/HSN and the rate, and they can be changed. The create sends `libraryItemId`. The server locks that Item `FOR SHARE` inside the transaction (`lockLibraryItems`), so CM-1102's delete (`FOR UPDATE`, then count) either waits and sees the new BOQ item (409 `ITEM_IN_USE`), or runs first and the copy gets 400 `BOQ_LIBRARY_ITEM_NOT_FOUND`. The HTTP test races the two six times.
- **Moves.** Sections and items move one place up or down (an item within its section), and positions are renumbered 0…n. Changing an item's section puts it at the end of the new one.
- **Delete guards.** A section is deleted only with no live items (409 `BOQ_SECTION_NOT_EMPTY`, `details.count`) and no pending extra item joining it (409 `VARIATION_PENDING`). An item cannot be deleted while a Variation of it is pending (409 `VARIATION_PENDING`). Deletes are tombstones, and the title or number is free again.
- **Financial.** Without BOQ Financial, every rate, amount, subtotal, total, the Order Value and the difference are `null`, and so are a Variation's rates and the library's adopted rate. The page shows quantities only. Without Financial the rate field is not shown and the server ignores any rate sent: a copied item gets the library's adopted rate, a typed one ₹0, and an edit keeps the rate. Rate changes and extra items need Financial (403), quantity changes do not. The Excel sample, import and export need Financial as well as their own flag (403), because the file carries rates.
- **Variations.** Numbers come from the `variation` sequence rule for the Project (`VAR/26-27/00001`), dated the Company's today, allocated inside the create's transaction. A Variation is raised with BOQ create. The reason is required (≤ 500). Each kind keeps only its own fields. A quantity or rate change records the figure it replaces at creation and again at approval. An extra item's number must be free among live items and other pending extra items (409 `BOQ_ITEM_NO_TAKEN`), checked again at approval. At most one pending quantity or rate change per item, whichever kind (409 `VARIATION_PENDING`, `details.number`). Approve and Reject use the approval kernel (`approve` / `reject`, `VARIATION_NOT_PENDING`, `REJECTION_REASON_REQUIRED`) with the BOQ's Approve and Reject flags. There is no Save & Approve, and the approver may be the creator. Approval applies the change in the same transaction, and an extra item becomes a BOQ item at the end of its section with `variation_id` set. A pending Variation can be edited (its kind is fixed) or deleted by whoever raised it while they hold BOQ create, or by a holder of BOQ update. Decided ones are final.
- **Notifications.** A Variation dispatches `document.submitted|approved|rejected` with the approval type `variation` (`APPROVAL_DOCUMENTS`, menu `contracts.boq`, link `…/boq?tab=variations`). Messaging turns these into `approval.requested` and `approval.decided` rather than a separate `variation.pending_approval` type. CM-1103 gave the BOQ menu the **Notification** flag (CRUDAJPNOFEI; ADR CM-0023 §4 updated), so a new Variation reaches the holders of BOQ Approve and Notification on the Project, and its creator hears of the decision when they hold BOQ Read and Notification. The Owner always does. The seeded Admin and Project Manager templates hold BOQ Notification, in `designations.json` and in the unshipped M11 menus migration (`20261021090500`), which was edited in place.
- **Deviation limit.** The Company's limit is in `construction_contracts.settings` (default 25 %, 0–100 with two places). `GET …/boq/settings` needs BOQ read, and `POST …/boq/settings/update` needs BOQ **Update**. Both are checked at Company level (the flag in the matrix, on no particular Project), because the setting covers every Project. The deviation list (`GET …/boq/deviations`) holds items whose checked measured quantity is more than `current × (1 + limit / 100)`, in BOQ order, with the % over (two places, half up) and any pending Variation. "Raise variation" opens a quantity change filled with the measured quantity.
- **Import.** One sheet (`BOQ`). Columns are found by header: Section, Item no, Description, UoM, SAC/HSN, Quantity, Rate (₹), Wing / Location, Library code. Sections are matched by title ignoring case, and new ones are added in first-seen order. Items are matched by Item no ignoring case. A new number adds an item at the end of its section. An existing number has its fields replaced (and moves to the end of a new section). A row identical to its item counts as `unchanged`. A Library code links the Item and fills blank Description, UoM, SAC/HSN and Rate from it. A blank code unlinks it. The UoM is matched by name, and the Wing or Location by name (an ambiguous name is a row error). A measured item's new quantity or rate is a row error on that column. Everything runs in one transaction inside the BOQ lock: all or nothing, 400 `IMPORT_HAS_ERRORS` with `details.errors` = [{ row, column, message }], at most 5,000 rows and 5 MB. The import writes one audit event per changed section and item (`source: "import"`) and one `boq.imported` summary.
- **Export.** The whole BOQ in order, with Original quantity, Quantity, Original rate (₹), Rate (₹) and Amount (₹) beside the sample's columns. Its Quantity and Rate (₹) columns import back unchanged, and the extra columns are ignored.
- **Audit.** `boq_section.created|renamed|moved|deleted`, `boq_item.created|updated|moved|deleted` (an approval's change carries `variationId`), `variation.created|updated|deleted|approved|rejected`, `contracts_settings.updated` and `boq.imported`.
- **No schema change.** The CM-1101 tables were enough. "One pending change per item" is kept by the lock, not a partial index.
- **Not yet.** Backups (CM-907) do not include the BOQ yet, as with the Item Library. Work Orders (CM-1104) should refuse to delete or renumber a BOQ item their lines name.

### CM-1104 — Work Orders

- **Where it is.** Project → Contracts → **Work Orders** (`/app/projects/{id}/work-orders`), with `/new`, `/{workOrderId}`, `/{workOrderId}/edit` (a draft) and `/{workOrderId}/amend` (an issued one). Approval notices link to the detail page.
- **HTTP shape.** Everything is under `/api/construction/contracts/work-orders`, Project-scoped like the BOQ: the list, create, `form-options`, `boq-items` and `material-options` name the Project (`?projectId=` or the body), and a Work Order is reached by its id (`/{id}`, `/{id}/update|delete|submit|approve|reject|amend|close|cancel`, `/{id}/pdf`). Access is checked first (403 `PERMISSION_DENIED`, then 404 `PROJECT_NOT_FOUND`); another Company's Work Order is 404 `WORK_ORDER_NOT_FOUND`. Every step answers with the whole Work Order, its warnings included.
- **Number.** A draft has **no number** (screens show “Draft”). The first submission takes one from the `work_order` sequence rule for the Project, dated the **order date** (so the fiscal-year token follows it). A rejection sends it back to draft and it keeps its number; a resubmission does not take another. A deleted draft's number is not reissued. No other numbered document had a draft state, so this needed `work_orders.number` to become nullable (the live-number partial unique index ignores nulls).
- **Migration `20261022090000_construction_contracts_work_order_advance_terms`** (`construction_contracts` only): `mobilisation_advance BIGINT NULL`, `mobilisation_recovery_percent DECIMAL(5,2) NULL`, `close_reason TEXT NULL` (the close reason had no column) and `number` nullable. Deployed to `construction_m11` and `construction_test_m11`.
- **Back-dated entry.** Work Orders join the policy as module `work_order` (“Work Order (WO)”, a new **Contracts** group, entry date `orderDate`, menu `contracts.work_orders`). A create checks the order date; an edit or amendment checks the stored date and, when it changes, the new one. Submit, approve, reject, close and cancel are not date edits and are not checked.
- **Parties.** The Contractor must be active and assigned to the Project (`ContractsDirectory.contractors`, 400 `WORK_ORDER_CONTRACTOR_INVALID`); one the Work Order already has may stay after it leaves the Project. The Department must be one of that Contractor's (400 `WORK_ORDER_DEPARTMENT_INVALID`), active or already on the Work Order. An amendment cannot change the Contractor (400 `WORK_ORDER_CONTRACTOR_FIXED`): cancel and raise a new one.
- **Terms.** Retention 0–100 % (blank 0), cap 0–100 % of value (blank: none), released on completion 0–100 % (blank 50), DLP 0–120 whole months, mobilisation recovery 0–100 %, all with two places. **GST** is a free 0–28 % with two places, matching the existing GST inputs (Materials, POs), and the form offers 0, 5, 12, 18 and 28. **SAC** is any 4–8 digit code; the form offers 9954, 9985 and 9987. **TDS nature** uses provisional keys in `contract-terms.ts` (`TDS_NATURES`: `contractor`, `professional`, `technical`, `rent_plant`, `rent_land`, `goods_purchase`) until CM-1116 brings finance's natures, which should adopt or map these keys. A new Work Order left without one gets `contractor` when the Contractor has TDS applicable, else none; an edit that leaves it out keeps it; null means no TDS.
- **Lines.** A BOQ line names a live BOQ item of the Project (400 `WORK_ORDER_BOQ_ITEM_INVALID`); its blanks come from the item (item no, description, UoM, SAC/HSN, the **current** rate) and its quantity defaults to what is left when that is more than 0, otherwise it must be typed. A non-BOQ line needs a description and UoM. 1–500 lines; quantity and rate as on the BOQ (four places; paise; amount ≤ ₹1,000 crore). A line sent back with its `id` keeps its id, **kind and BOQ item**; lines not sent are tombstoned (their ids stay valid for bills); positions follow the order sent.
- **Remaining quantity** = BOQ current quantity − Σ quantity on live lines of the Project's other live Work Orders that are **not cancelled** (closed ones still count). More than that is a **warning**, never a refusal: `warnings[]` (`WORK_ORDER_QUANTITY_OVER_REMAINING`, per BOQ item with this Work Order's lines added up, `ordered`, `remaining`, `message`) on create, update, amend and the detail of a draft, pending or issued Work Order. The form shows the same warning while you type.
- **Financial.** As CM-1103: without `contracts.work_orders` Financial every rate, amount, value, the mobilisation advance and the material issue and penal rates are `null`, and rates sent are ignored. A kept line keeps its rate, a new BOQ line takes the BOQ's current rate, a non-BOQ line ₹0; a kept advance stays; a new at-cost material takes the Material's unit rate. The form hides those fields and the total.
- **Materials issued** (CM-0023 §10). One row per Material (400 `WORK_ORDER_MATERIAL_DUPLICATE`), at most 100, an enabled Material (or one already on the Work Order). Issue basis free or at cost (an at-cost row needs its issue rate; a free one drops it), wastage 0–100 %, optional penal rate. Coefficients are per line, sent by the line's **index**; a line left out takes the Material's coefficient in the rate analysis of the line's BOQ item's library Item (several analysis lines of one Material add up), a blank one means none. The form prefills them when a Material is picked or a BOQ line added, and sends every one. Saving replaces the rows (new ids); an edit that leaves `materials` out keeps them, minus coefficients of removed lines. CM-1110 should key reconciliation on (Work Order, Material), not the row id.
- **Life and flags.** Draft → submit → pending approval → approve → **issued**, or reject (reason) → draft with `reject_reason` shown until resubmitted. Create needs Create; editing, submitting a draft: Update, or Create for its creator; deleting a draft: Delete, or Create for its creator; Approve and Reject their flags (the approval kernel's `approve`/`reject`; 409 `WORK_ORDER_NOT_PENDING` is checked first so the message names the real status; 400 `REJECTION_REASON_REQUIRED`); **close and cancel need Update**. Any other step in the wrong status is 409 `WORK_ORDER_STATUS_INVALID` (`details.status`, `details.action`). There is no Save & Approve; the approver may be the creator.
- **Amendment.** Update **and** Approve, a reason (400 `AMENDMENT_REASON_REQUIRED`), and the same form as an edit. **No second approval round**: the amender holds Approve, so it takes effect at once and stays issued. The revision row keeps the revision it replaced (`revision` = the old number) with **the reason it was amended**, and a JSON snapshot of the header, terms, lines (with UoM names), value and materials (with names), so an old revision reads the same after a master is renamed; the Work Order's `revision` goes up by one. A line on an **approved** bill (`bill_lines.work_order_line_id` on a live bill with status `approved`) cannot be removed (409 `WORK_ORDER_LINE_BILLED`, `details.lineId`) or cut below the billed quantity (409 `WORK_ORDER_QUANTITY_BELOW_BILLED`, `details.lineId`, `details.billed`). The detail shows each line's billed quantity.
- **Close and cancel.** Close an issued Work Order with a date on or after the order date (400 `CLOSED_ON_BEFORE_ORDER_DATE`) and a reason; refused while a live bill on it is draft or pending approval (409 `WORK_ORDER_BILL_OPEN`, `details.count`). The close date becomes the completion date (DLP start) when none was recorded. Cancel a draft or issued Work Order with a reason, dated the Company's today; refused once an approved bill names one of its lines (409 `WORK_ORDER_BILLED`: close it instead) or while a bill is open. A cancelled Work Order's lines stop counting against the BOQ.
- **Optimistic checks.** Update and amend need `expectedUpdatedAt`; delete, submit, approve, reject, close and cancel check it when sent (409 `WORK_ORDER_CHANGED`); the screens always send it.
- **One writer per Project.** Every Work Order command takes the BOQ's advisory lock (`construction_contracts.boq:{workspace}:{project}`), so Work Order and BOQ changes on a Project never cross: the remaining quantity and the BOQ delete guard read committed lines.
- **BOQ guard (CM-1103 follow-up).** A BOQ item named by a live line of a live, non-cancelled Work Order cannot be deleted: 409 `BOQ_ITEM_IN_WORK_ORDER`, `details.workOrders` (their numbers, “Draft” for one never submitted), checked inside the BOQ lock. The BOQ import never deletes items, so it needs no guard. Renumbering a BOQ item stays allowed: a Work Order line keeps its own copy of the item no. The BOQ's delete dialog says that an item a Work Order names cannot be deleted, and shows the server's message naming the Work Orders.
- **Notifications.** Submit, approve and reject dispatch `document.submitted|approved|rejected` with approval type `work_order` (`APPROVAL_DOCUMENTS`, menu `contracts.work_orders`, link to the detail page): messaging's `approval.requested` is the ticket's `work_order.pending_approval`, as with Variations. Approval also raises **`WorkOrderIssued`**, which messaging turns into **`work_order.issued`** (“Work Order WO/… is issued”, “To {Contractor} in {Project}.”) for Work Order Read + Notification holders on the Project, never the approver — the same kind of non-approval notice as `booking.created`. The menu already had the Notification flag (CRUDAJPNOF).
- **PDF.** `GET …/{id}/pdf` needs **Print**. The Purchase Order's page writer moved to `src/shared-kernel/pdf/document-pdf-writer.ts` (procurement re-exports it) so contracts can use it: A4, embedded Noto fonts, wrapped cells, a header that repeats on each page. It prints the Company letterhead, the Project (site address, state, Client), the number, revision, status and dates, the Contractor and Department (address, GSTIN / PAN), the scope note, the line table (item no, description, UoM, qty, rate, amount) with the total, the terms, the materials issued, and signature blocks for the Contractor and the Company. Without Financial it prints quantities only (no rates, amounts, total or advance amount). `?inline=1` opens it in the browser.
- **Audit.** `work_order.created|updated|deleted|submitted|approved|rejected|amended|closed|cancelled`; the amendment carries its reason. Snapshots hold the header, terms, line count and value.
- **Screens.** The list filters by status, Contractor (shown to Work Order editors, whose form options list the Contractors) and a search on number or scope; cards at phone width, a table above. The form has a header card, a terms card, the lines table (scrolls inside its frame) with **Add from BOQ** (a dialog with what each item has left, several at once) and **Add line**, the live warning, a running total, and the materials panel that opens on demand. The detail shows the status, actions behind their flags (Edit, Amend, Submit, Approve, Reject, More → Close / Cancel / Delete, Download PDF), the reject, close or cancel reason, the warnings, the terms, lines with billed quantities, materials and the revisions, each opening to its old terms and lines.
- **Not yet.** Backups (CM-907) do not include Work Orders yet, as with the BOQ. Advances themselves (CM-1108), bills (CM-1106), escalation (CM-1109) and reconciliation (CM-1110) build on these tables.

### CM-1105 — Measurement Book

- **Where it is.** Project → Contracts → **Measurements** (`/app/projects/{id}/measurements`), with `/new?side=client|contractor` and `/{sheetId}`. One page per sheet: a draft the viewer may change is edited in place; a submitted, checked or billed sheet reads only. `measurement.submitted` links to the sheet. The `measurements` stub left `CONTRACTS_MODULE_TICKETS`.
- **HTTP shape.** Everything is under `/api/construction/contracts/measurements`, Project-scoped like the BOQ and Work Orders: the list, create, `form-options` and `quantities` name the Project, and a sheet is reached by its id (`/{id}`, `/{id}/update|delete|submit|check|return|reopen`, `/{id}/photos/**`). Access is checked first (403 `PERMISSION_DENIED`, then 404 `PROJECT_NOT_FOUND`); another Company's sheet is 404 `MEASUREMENT_NOT_FOUND`. Every step answers with the whole sheet, its rows, the cumulative panel and `allowed` (what the caller may do now).
- **Menu Notification flag.** `contracts.measurements` is **CRUDAPNO** (ADR CM-0023 §6 updated), so a submitted sheet reaches the holders of Approve + Notification. The seeded Admin and Project Manager templates hold it, in `designations.json` and in the unshipped M11 menus migration (`20261021090500`, edited in place as CM-1103 did). Both M11 databases had recorded an older checksum for that migration (before CM-1103's edit): the grants SQL was run again (it only ORs bits, so it is idempotent) and `_prisma_migrations.checksum` was set to the file's SHA-256, so `migrate deploy` is clean on `construction_m11` and `construction_test_m11`.
- **Sides.** A sheet's side and Work Order are fixed when it is created (delete the draft to start again). The **client side** measures live BOQ items of the Project and names no Work Order (400 `MEASUREMENT_WORK_ORDER_NOT_ALLOWED`). It is allowed on **Own development** Projects too: there the BOQ is a budget and is never billed, but measuring it tracks progress, and checked rows lock BOQ items just the same. The **contractor side** needs one Work Order of the Project that is **issued** (400 `MEASUREMENT_WORK_ORDER_REQUIRED` / `MEASUREMENT_WORK_ORDER_INVALID`), checked on create, edit, submit and check; its rows name live lines of that Work Order. A row naming the other side's item, or a line of another Work Order, is 400 `MEASUREMENT_ITEM_INVALID` with `details.row` and `details.field` (`rows.N.boqItemId` / `rows.N.workOrderLineId`).
- **The quantity rule.** `quantity = nos × (the product of the filled dimensions)`. Length, breadth and depth/height may each be blank (left out, not 0); a blank nos is 1, so nos alone counts pieces. Every number has at most four decimals; the product is rounded **once**, half up (away from zero for a deduction), to four decimals — never per factor. A row may instead be **direct**: the quantity is typed and nos and the dimensions are dropped. Dimensions are more than 0, nos is not 0, a direct quantity is not 0, and a row that works out to 0.0000 is refused (`MEASUREMENT_DIMENSION_INVALID`, `MEASUREMENT_NOS_INVALID`, `MEASUREMENT_QUANTITY_INVALID`, `MEASUREMENT_QUANTITY_ZERO`). |quantity| stays below 10¹² (`DECIMAL(16,4)`).
- **Deductions** are a **negative nos** (or a negative direct quantity), not a toggle: one number carries the sign, nothing new is stored, and a deduction row reads as "−1 × 0.9 × 2.1". Screens mark it "Deduction".
- **Rows.** At most 500 a sheet; a description of at most 500; an optional `LocationRef` checked by the Project's location resolver (errors carry `details.row`). Saving a draft replaces its rows (new ids): nothing points at a draft's rows. The form is the site-work location picker in a dialog per row.
- **Header.** Measured on (not in the future, 400 `MEASURED_ON_IN_FUTURE`), a title (≤ 120) and remarks (≤ 2,000, line breaks kept).
- **Back-dated entry.** Module `measurement` ("Measurement Book", the Contracts group, entry date `measuredOn`, menu `contracts.measurements`). A create checks the date measured; an edit checks the stored date and, when it changes, the new one. Submit, check, return, reopen and delete are not date edits.
- **Life and flags.** Draft → submit → **submitted** → check → **checked**. Create needs Create. Editing and submitting a draft: its creator with Create, or Update. Submit needs at least one row (400 `MEASUREMENT_ROWS_REQUIRED`). **Check, return and reopen need Approve** (403 otherwise); the checker may be the drafter. Any step in the wrong status is 409 `MEASUREMENT_STATUS_INVALID` (`details.status`, `details.action`). **Delete** is allowed in any status: a draft by its creator with Create or a Delete holder, a submitted or checked sheet by a Delete holder only (a tombstone; a checked one stops counting as measured).
- **Check (the joint measurement).** Records `checked_by` = the caller (our engineer), `checked_at`, and the other party's `party_name` (≤ 120) and `party_role` (≤ 80), both required, and `joint_on`: required, on or after the date measured (400 `JOINT_ON_BEFORE_MEASURED_ON`) and not after the Company's today (400 `JOINT_ON_IN_FUTURE`).
- **Return and reopen.** Return sends a submitted sheet back to draft with a reason (400 `RETURN_REASON_REQUIRED`, ≤ 500), clearing who submitted it. Reopen sends a checked sheet back to submitted with a reason (400 `REOPEN_REASON_REQUIRED`) and **clears the joint measurement** (checker, party, date — the audit keeps them), so its rows stop counting as measured until it is checked again. The reasons had no columns: migration `20261022120000_construction_contracts_measurement_photos` adds `return_reason` and `reopen_reason` to `measurement_sheets`; each is shown until the sheet is submitted (return) or checked (reopen) again.
- **Billed is read-only.** Once any row has a `bill_id`, edit, submit, delete, check, return, reopen and photo changes are refused with 409 `MEASUREMENT_BILLED` (`details.count`), checked before the status so the message names the real reason. CM-1106 sets and clears `bill_id`; the tests set it directly.
- **One writer per Project.** Every Measurement Book command (both sides, photos too) takes the BOQ's advisory lock (`construction_contracts.boq:{workspace}:{project}`), so a check, reopen or delete and a BOQ edit or Work Order change never cross. The HTTP test shows CM-1103's `BOQ_ITEM_MEASURED` tripping from a real checked sheet and clearing on reopen. Optimistic `updatedAt` on every change: update needs `expectedUpdatedAt`; the other steps check it when sent (409 `MEASUREMENT_CHANGED`); the screens always send it.
- **Cumulative and deviation.** Per item of a sheet: `checked` = Σ rows on the Project's **other** live checked sheets of that side naming it, `thisSheet` = Σ this sheet's rows (whatever its status), `total` = the two, against `planned` = the BOQ item's **current** quantity (client) or the Work Order line's quantity (contractor). `over` when total > planned. A row is marked `over` (shown as "Deviation" / "Over WO") when, walking the sheet's rows in order from `checked`, it adds to the item (not a deduction) and the running total after it is above planned. Client side: `overLimit` when the total is beyond the Company's deviation limit (`isDeviation`, CM-1103), with the % over (two places, half up) and a link to the BOQ's Deviations tab (which lists checked quantities only). Contractor side: no limit; each over line is a warning naming 409 `WORK_ORDER_QUANTITY_EXCEEDED`, which CM-1106 will raise when a bill takes more than the Work Order holds — amend the Work Order first.
- **Quantities read.** `GET …/measurements/quantities?projectId&side[&workOrderId]` (Read) lists every live BOQ item, or every live line of one Work Order, with `checked` (live checked sheets) and `pending` (submitted, not yet checked), and the same marks. The form adds its rows to `checked` in the browser with the same domain functions, so the marks move while you type.
- **Form options.** `GET …/form-options` (Create or Update) answers the Project's role and structure, the Client's name, the BOQ's live items in section order with their current quantity, and the **issued** Work Orders (up to 500) with their live lines.
- **Photos.** Through the attachments service (CM-0014) like a Daily Worksheet's: images only (PNG, JPEG, WebP), 25 MB each, 20 a sheet (409 `DOCUMENT_FILES_LIMIT`), WebP thumbnails, `stored_files` kind `measurement_photo`, keys under `measurement-photos/<sheetId>`. They are kept in the new `construction_contracts.measurement_photos` table and **not** indexed in the Project Gallery (the sheet is evidence for a bill, not site progress). Read sees them; Create or Update adds them; Update removes any, Create only one's own; none of it once billed.
- **Notifications.** Submit raises **`MeasurementSubmitted`** after commit; messaging turns it into **`measurement.submitted`** ("Measurement sheet of 20/10/2026 is ready to check", the side, party, title and row count) for Measurement Book **Approve** + Notification holders on the Project, never the submitter — like CM-1104's `work_order.issued`. Check, return and reopen send no notice yet.
- **Audit.** `measurement_sheet.created|updated|deleted|submitted|checked|returned|reopened` (return and reopen carry the reason), `measurement_photo.added|removed`. Snapshots hold the side, Work Order, date, status, title, the joint measurement, the row count and the total quantity.
- **Screens.** The list filters by side, status and (for editors, whose form options list them) Work Order; cards at phone width, a table above. A sheet shows its status and actions by `allowed` (Submit for checking, Check, Return to draft, Reopen, Delete), the return or reopen reason, the over-Work-Order warning, then the rows — while a draft, as a form whose rows show their quantity as you type, with add, duplicate and remove, a searchable item picker and a per-row location dialog — the "Measured to date" panel and the photos. Check opens a dialog for the other party's name, role and the date. At 375 px each row is a card with nos, L, B and D/H in a 2×2 grid, and nothing scrolls sideways.

A BOQ item or Work Order line named only by draft or submitted rows can still be deleted or amended away; such a row then fails its next save (400 `MEASUREMENT_ITEM_INVALID`) and shows "Item removed".
